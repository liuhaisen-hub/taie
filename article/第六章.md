1. 本章目标

结束时你将得到：

- 工具配置落库：web_search 的 apiKey / 搜索地址不再写死在 Go 代码里，而是存进 SQLite，设置页可编辑、可启停，重启不丢；`make seed` 幂等灌库，模板升级时按参数名合并，不覆盖用户已填的值；

2. 全景：从"三张脸"到"三件事"

第三章引入 web_search 时，它只有一张脸——`agentkit/toolkit/search.go` 里的一个函数，apiKey 硬编码在结构体里。本章的第一件事是把工具拆成三张脸，分别住在三个地方：

- **代码里的 builder**（`internal/agentkit/toolkit`）：知道*怎么*构建一个 eino 工具实例；
- **数据库里的配置行**（`tools` 表）：知道这个工具*用什么参数*、*开没开*；
- **前端的管理页**（设置 / 工具）：给人改参数、拨开关的地方。

分工原则一句话：**配置在数据里，构建在代码里**。代码里只保留"给定参数，我能造出这个工具"的能力（builder + 注册表），一切会变的东西（key、地址、开关）都下沉到数据库。

但配置落库只解决了"工具有没有"，没解决"工具干了什么看得见"。第五章的 stage 卡片方案（`MessageMeta.Stage/StageText`）在真实工具调用面前暴露了三个问题：卡片没有身份（连续多次调用无法配对）、词表是自造的（Semi 不认识，全靠自定义渲染）、流式 `tool_calls` 分片没有归位键。于是本章第二件事：**协议推倒重来**，第三件事：**把会话底座按"agent 干活"重塑**（表结构瘦身 + checkpoint）。

三条数据流拉通看：

```
tool.json ──make seed──► tools 表 ──设置页编辑/启用──► enable=1
                                                   │
       ToolsNodeConfig ◄── registry 构建 ◄── ListEnable（会话首次运行时拉取）

前端 JSONStream("agent/chat") ──► AgentServices ──► ChatAgent.Runner
                                                      │ emitter（本章新增）
   Semi AIChatDialogue ◄── events v3（ContentItem）◄──┘
   （function_call 原生渲染 + tool_result 自定义折叠卡）
```

- **删 `tool_ids` / `max_history`**：第五章为"工具快照进会话"预留的槽位，本章直接拆除——工具集的去留问题用删除做了了结：**工具集跟随全局启用状态**，会话只在内存里缓存一份（见 6.4），"重启后漂移"成为既定语义而非待定问题；

3.2 chat_message：status 列退役，Extra 上位

消息表（migrations/creat_message.sql——文件名笔误又回来了，遗留清单 +1）：

```sql

    deleted_at TIMESTAMP NULL

```

变化的核心是一笔交换：**第五章的 `status INTEGER` 列没了，换成 `extra` JSON 扩展字段**。落库时状态写进 Extra：

```go
// internal/data/agent.go
// AppendAssistantMessage 落库一条 assistant 消息，status 存在 Extra 扩展字段中
func (a *agentRepo) AppendAssistantMessage(ctx context.Context, sessionID uint, content string, status int) error {
    extra, err := json.Marshal(map[string]int{"status": status})
    if err != nil {
        return err
    }
    return a.data.db.WithContext(ctx).Create(&po.ChatMessage{
        SessionID: uint64(sessionID),
        Role:      po.AssistantRole,
        Content:   content,
        Extra:     extra,
    }).Error
}
```

值得停下来想一秒的取舍：为什么把结构化的 status 藏进 JSON？

- **重放时它是多余的**：模型重放历史只关心 role/content（`buildMessage` 只消费这两列），status 是"给人看"的展示元数据——0 完成 / 1 被中断 / 3 出错，将来前端渲染"已中断"角标时从 Extra 读；
- **扩展免迁移**：下一章要落库 token 用量、引用列表时，Extra 里加个 key 就行，不用动表；
- **代价是查询能力**："找出所有被中断的消息"没法走索引。但历史回放 UI 还没做（历史 Tab 是本章的占位），等真需要时再加生成列也不迟。

`tool_calls` / `multi_content` / `name` 列继续保留——v2 全保真回放的预留位没动。

4. 协议 v3：ContentItem，一张卡片一个身份

4.1 stage 卡片为什么活了一章就死

第五章的 stage 方案是：工具事件统一发一张 `MessageMeta{Stage: "tool_call", StageText: "调用工具 web_search"}` 卡片，前端自定义渲染。放到真实场景里它撑不住：

1. **没有身份**：`Meta` 里只有工具名，模型一轮里连续调两次 web_search，两张卡无法区分先后、无法配对"调用→结果"；
2. **词表是自造的**：`thinking/tool_call/retrieve/answer` 这套阶段词表 Semi 一个都不认识，全要自定义渲染——而 Semi 明明内置了 `function_call` 的卡片渲染和 `in_progress/completed` 状态语义；
3. **分片无处安放**：流式模式下 `tool_calls` 的参数是按 `Index` 分片到达的（第五章 v1 明确不做聚合），聚合完的调用需要一个 ID 才能和结果对上。

所以 v3 直接换词表：**Message.content 统一为 ContentItem 数组，形态对齐 OpenAI Response Object（也就是 Semi ContentItem 的原生形态）**：

```go
// internal/pkg/events/response.go —— 状态与 item 类型，全部对齐 Semi / OpenAI 原生取值
const (
    StatusLoading    = "in_progress"
    StatusDone       = "completed"
    StatusError      = "failed"
    StatusIncomplete = "incomplete" // 中断（stop/断连）收口
)

const (
    ItemMessage      = "message"
    ItemOutputText   = "output_text"
    ItemFunctionCall = "function_call"
    ItemToolResult   = "tool_result" // 自定义：Semi 无此类型，前端注册折叠卡渲染
)

// ContentItem 是 OpenAI Response Object 子集，字段名与 Semi ContentItem 一致，
// 前端收到后直接作为 Message.content 数组元素塞进 AIChatDialogue，零转换。
type ContentItem struct {
    Type      string        `json:"type,omitempty"`
    Status    string        `json:"status,omitempty"`
    Text      string        `json:"text,omitempty"`    // output_text：delta 里是增量，done 里是全文
    Content   []ContentItem `json:"content,omitempty"` // message item 的内层元素
    CallID    string        `json:"call_id,omitempty"` // function_call / tool_result 的归位键
    Name      string        `json:"name,omitempty"`
    Arguments string        `json:"arguments,omitempty"` // 分片累积后的完整 JSON 串
    Result    string        `json:"result,omitempty"`
}
```

一个踩过才认识的坑写在注释里：**Semi 只内置渲染 `message / reasoning / function_call` 等几种顶层 item，裸 `output_text` 放 `Message.content` 顶层不会被渲染**。所以正文必须包一层：

```go
// MessageItem 把正文包裹成 message item，Semi 才渲染
func MessageItem(text string) ContentItem {
    return ContentItem{Type: ItemMessage, Content: []ContentItem{{Type: ItemOutputText, Text: text}}}
}
```

4.2 事件构造器

| 构造器 | kind | content | status | 说明 |
| --- | --- | --- | --- | --- |
| `Begin(sessionID)` | begin | — | — | message.id 携带会话 ID；**services 层构造，agentkit 不发** |
| `Delta(assistantID, chunk)` | delta | `[{output_text, 增量}]` | in_progress | 文本增量，前端追加进最后一个 message item |
| `ToolCall(assistantID, callID, name, args)` | tool_call | `[function_call]` | — | item 自带 status=in_progress，Semi 原生渲染 |
| `ToolResult(assistantID, callID, result)` | tool_result | `[{tool_result, call_id, result}]` | — | 前端按 call_id 把对应 function_call 置 completed |
| `Done(assistantID, items)` | done | 服务端重组的完整 seq | completed | 整体替换气泡内容 |
| `Interrupted(assistantID, items)` | done | 已累积 seq | **incomplete** | 复用 done 通道，前端按 status 区分置 cancelled |
| `Error(text)` | error | `[{output_text, 文案}]` | failed | 错误文案追加展示 |

和 v2 的三点不同：`stage` 没了（被 `tool_call/tool_result` 取代）；每条事件都带 `assistantID`（前端把占位气泡归并到同一条消息）；`done` 从"全文一个字符串"变成"完整内容序列"——见下一节的 emitter。


5. emitter：把一轮生成收口成一条事件流

5.1 Runner 主流程

```go
// internal/agentkit/chatagent.go（节选）
func (c *ChatAgent) Runner(ctx context.Context, sessionID uint, query string,
    b *provider.BuildParams, onEvent func(events.Event) error) error {

    e, err := c.getOrCreate(ctx, sessionID, b)
    if err != nil {
        return onEvent(events.Error(fmt.Sprintf("初始化模型失败: %v", err)))
    }
    agent, err := c.buildAgent(ctx, e)
    if err != nil {
        return onEvent(events.Error(fmt.Sprintf("构建 Agent 失败: %v", err)))
    }
    // 用户消息先落库，防止其他问题中断
    if err := c.repo.AppendUserMessage(ctx, sessionID, query); err != nil { ... }
    // 读取历史（已包含刚落库的用户消息）
    message, err := c.buildMessage(ctx, sessionID)

    runner := adk.NewRunner(ctx, adk.RunnerConfig{
        Agent:           agent,
        EnableStreaming: true,
        CheckPointStore: c.cpStore, // ⬅ 本章接入，见第 9 节
    })
    agevs := runner.Run(ctx, message, adk.WithSessionValues(map[string]any{
        "Now": time.Now().Format("2006-01-02 15:04:05"),
    }))

    em := newEmitter(sessionID, onEvent)
    for {
        agev, ok := agevs.Next()
        if !ok { break }
        if agev.Err != nil {
            if ctx.Err() != nil {
                // 中断：已生成的部分按退出状态落库，并尽力回推 incomplete 收口
                _ = c.repo.AppendAssistantMessage(ctx, sessionID, em.Text(), po.MessageExitStatus)
                _ = em.interrupted()
                return ctx.Err()
            }
            return onEvent(events.Error(agev.Err.Error()))
        }
        out := agev.Output.MessageOutput
        if out == nil { continue }
        // Role 挂在 MessageVariant 上，流式模式下不消费流就能判断
        if out.Role == schema.Tool {
            // 工具回执：call_id 在 tool 消息上，前端按 call_id 把 function_call 置 completed
            content, callID := "", ""
            if out.IsStreaming && out.MessageStream != nil {
                content, callID = drainToolStream(out.MessageStream)
            } else if out.Message != nil {
                content, callID = out.Message.Content, out.Message.ToolCallID
            }
            if err := em.toolResult(callID, content); err != nil { return err }
            continue
        }
        if out.IsStreaming {
            if err := em.consumeStream(out.MessageStream); err != nil {
                if ctx.Err() != nil {
                    _ = c.repo.AppendAssistantMessage(ctx, sessionID, em.Text(), po.MessageExitStatus)
                    return ctx.Err()
                }
                return onEvent(events.Error(fmt.Sprintf("执行错误: %v", err)))
            }
        } else if out.Message != nil {
            // 非流式兜底：必须与流式分支同级，嵌进流式分支会吞掉非流式模型的输出
            if err := em.assistantMessage(out.Message); err != nil { return err }
        }
    }
    // 完成落库，Done 事件与落库内容同源
    _ = c.repo.AppendAssistantMessage(ctx, sessionID, em.Text(), po.MessageFinishStatus)
    return em.done()
}
```

骨架和第五章一致（落库时机、中断分支、非流式兜底都还在），变化是把"事件拼装"从循环里抽出去，交给 `emitter`。循环里只剩三种语义：工具回执 → `em.toolResult`；流式 assistant → `em.consumeStream`；非流式 → `em.assistantMessage`。另外 `adk.NewChatModelAgent` 配置里补了 `MaxIterations: 20`，工具循环不再能无限转下去。

5.2 emitter 的账本

```go
// emitter 收口一轮问答的事件发射：持有本轮 assistant 消息 ID 与按发生顺序累积的
// 内容序列。delta/tool_call/tool_result 即时下发，done 时重组完整 ContentItem[]
// 作为最终态整体下发，保证与事件流一致。
type emitter struct {
    assistantID string
    onEvent     func(events.Event) error

    textBuf     strings.Builder      // 正文全文（与落库同源）
    seq         []events.ContentItem // 内容序列：message 全文项 + function_call + tool_result
    callIdx     map[string]int       // call_id -> seq 中 function_call item 下标
    streamText  strings.Builder      // 当前流式消息的正文（EOF 时并入 seq）
    streamIdx   map[int]*toolCallAcc // 当前流式消息的工具调用分片聚合
    streamOrder []int                // 分片出现顺序，保证下发顺序稳定
}
```

四个设计点：

1. **assistantID 由 agentkit 生成**（`assistant-{sessionID}-{unixnano}`）。落库在结束时才发生，拿不到自增主键，所以本轮所有事件全程携带这个临时 ID，前端据此把占位气泡归并到同一条消息上；
2. **seq 是"账本"，事件是"流水"**。delta/tool_call/tool_result 即时下发保证低延迟，但流式归并可能漂移（乱序、重试），所以 done 时把 seq 整体重组下发作为最终态，前端整体替换——**前端兜底和事件流永远一致**；
3. **流式 tool_calls 分片聚合**（第五章明确 v1 不做的，这里做了）。eino 的 `chunk.ToolCalls` 按 `Index` 分片，Name/ID 可能只在首片出现，Arguments 逐片追加；EOF 时 Name/Arguments 才拼装完整，所以聚合器在 `streamEOF` 里统一下发：

```go
// consumeStream 消费一条流式 assistant 消息（节选）
for i := range chunk.ToolCalls {
    tc := chunk.ToolCalls[i]
    idx := 0
    if tc.Index != nil { idx = *tc.Index }
    acc := e.streamAcc(idx)          // 取/建该 Index 的聚合器
    if tc.ID != "" { acc.id = tc.ID }
    if tc.Function.Name != "" { acc.name = tc.Function.Name }
    acc.args.WriteString(tc.Function.Arguments)
}
```

4. **一轮 Run 里 assistant 消息可能有多条**（每次工具调用前后各一条）。`streamEOF` 在每条流结束时把正文并成一个 message item 入 seq、把攒好的 function_call 统一下发，然后重置流内聚合；`callIdx` 跨流共享——工具回执到达时按 `call_id` 从账本里找到对应 function_call 置 completed，结果追加为 tool_result item。

落库与 Done 同源的承诺没变：`em.Text()` 返回 `textBuf` 全文，正常收口 `AppendAssistantMessage(..., MessageFinishStatus)`，中断收口 `MessageExitStatus`。


6. 工具配置落库

6.1 tools 表与 CommonJson

```sql
-- migrations/create_tools.sql
CREATE TABLE IF NOT EXISTS `tools` (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    tool_name VARCHAR(50) NOT NULL,
    args TEXT CHECK(json_valid(args)),      -- 配置参数，CommonJson 数组的 JSON
    desc VARCHAR(100),
    info VARCHAR(100),
    created_at DATETIME,
    updated_at DATETIME,
    deleted_at DATETIME,
    enable INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_enable_deleted_at on tools(enable, deleted_at);
CREATE INDEX IF NOT EXISTS idx_deleted_at_name on tools (tool_name, deleted_at);
```

配置参数的载体仍是 `po.CommonJson` 三件套：

```go
// internal/po/tool.go
type CommonJson struct {
    Label string `json:"label"` // 字段名，作为表单的 key
    Name  string `json:"name"`  // 展示名，表单 label 显示用
    Value string `json:"value"`
}
```

`label` 给机器（存库 key、表单 field），`name` 给人（"豆包密钥" vs "apiKey"），`value` 是值。这个 JSON 数组是前后端共享的契约：后端按 label 取值构建工具，前端按数组渲染表单，中间任何一方都不需要认识"apiKey"这个具体字段。代价是失去类型约束（value 全是 string、拼错 label 静默失效）——遗留清单老面孔。

值得记一笔的销账方式：第六章写作时的遗留清单第 1 条——`ListEnable` 里 `Where("enable = ?")` 与列名 `enabled` 不一致——最终**不是改查询，而是把列改了**：迁移里列名统一为 `enable`，PO 字段 `Enable int32`。一条 SQL 字符串绕过 GORM 字段映射的事故，用"让字符串和列名重新一致"收场。不过三个名字里仍有俩叫法：数据库列 `enable`、Go 字段 `Enable`、JSON 字段 `enabled`（前端 `tool.enabled === 1`）——轻度不对称，能用，但看着别扭。

另一个边界约定不变：**工具是内置固定项，不能增删**。`tools` 表没有 Create/Delete，服务层只暴露 List / Update / Enable——本章的工具系统是"管理"而非"商店"，上传第三方工具留给 MCP。

6.2 种子机制：tool.json 与 mergeArgs

```json
// tool.json（项目根目录）
{
```

有业务含量的仍是 data 层的 `Enable`——**参数没配置的工具不许启用**：

```go
// internal/data/tools.go
func (t *toolsRepo) Enable(ctx context.Context, id uint, enable int32) error {
    return t.data.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
        var tool po.Tool
        if err := tx.Where("id = ?", id).First(&tool).Error; err != nil {
            return err
        }
        if tool.Args == "" {
            return fmt.Errorf("未设置相关配置")
        }
        return tx.Model(&po.Tool{}).Where("id = ?", id).Update("enable", enable).Error
    })
}
```

守卫放在事务里做"先读后写"，错误信息跨过 Wails 调用边界原样返回：Go `error` → 前端 Promise reject → Toast。放在 data 层而非 services 层是有意的：将来别的调用方绕过 services 直接操作 repo，守卫依然生效。（它只拦空字符串、拦不住 `[]` 的老问题依旧——遗留清单。）

6.4 agentkit：registry、BuildTools 与 ListEnable

```go
// internal/agentkit/toolkit/tookit.go
// ToolBuilder 由 tools.args 中的 JSON 字符串构建工具实例。
type ToolBuilder func(args string) (tool.InvokableTool, error)

var registry = map[string]ToolBuilder{
    "web_search": buildWebSearch,
}

func BuildTools(active map[string]string) []tool.BaseTool {
    if len(active) <= 0 { return nil }
    tools := make([]tool.BaseTool, 0, len(active))
    for n, a := range active {
        build, ok := registry[n]
        if !ok { continue }        // DB 启用了但代码没实现：不报错，跳过
        t, err := build(a)
        if err != nil { continue } // 配置缺失构建失败：同样跳过
        tools = append(tools, t)
    }
    return tools
}
```

`BuildTools(active)` 的入参是 `map[工具名]argsJSON`——正好是 DB 的形状。两个 `continue` 的静默语义是刻意的：一个工具配置坏了不该炸掉整场对话，代价是"配了但没生效"只能靠发现（目前连日志都没有，遗留清单老面孔）。

8. 停止生成闭环 v2

第五章的设计是"用户停止 → ctx 取消 → 半截回答按 status=1 落库"，上一版补了停止按钮但收口事件还是借道 error。本章给它配了正式的收口协议：

```tsx
// frontend/src/hooks/aichat/provider/provider.tsx
/** 停止生成：关闭连接 → Go 侧 ctx 取消 → 模型推理中断，气泡置 cancelled */
const stop = useCallback(() => {
    finish("cancelled");
}, [finish]);
```

链路：Semi 输入框停止按钮 → `stop()` → `finish("cancelled")`（取消 rAF 排程、清缓冲、关闭 JSONStream 连接、气泡置 cancelled）→ Wails 取消该次服务调用的 ctx → Runner 事件循环 `agev.Err != nil && ctx.Err() != nil` 命中 → `AppendAssistantMessage(em.Text(), MessageExitStatus)`（状态进 Extra）→ `em.interrupted()` 尽力回推 `events.Interrupted`（kind=done + status=incomplete；连接已关，发射失败静默）→ 前端若还在线则把气泡内容整体替换为服务端已累积的 items。

另有一条断连兜底：非 done/error 路径的连接异常断开（窗口刷新、网络抖动）也走收口——

```tsx
// 连接异常断开（非 done/error 路径）也要收口
socket.onclose = () => {
    if (socketRef.current === socket) finish("cancelled");
};
```

一次问答 = 一个连接，生命周期清晰、取消天然生效。写入时机表更新为 v3 版：

| 时机 | 前端气泡 | DB |
| --- | --- | --- |
| Run 开始前 | 用户气泡立即回显 | 用户消息 |
| delta / tool_call / tool_result | 即时归并（rAF 合帧） | — |
| 正常收口 `done(completed)` | 整体替换为服务端重组 seq | assistant 全文，Extra.status=0 |
| 中断收口 `done(incomplete)` | cancelled | 已生成文本，Extra.status=1 |
| 出错 `error(failed)` | 追加"出错了：…" | （不落库，见遗留清单） |
