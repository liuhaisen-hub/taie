1. 本章目标

第八章结尾的许诺本章到岗："审批进场，Agent 第一次学会先问过用户再动手"。结束时你将得到：

- **权限模型**：`manual` / `plan` / `auto` 三种工作模式 + 六个内置工具的授权开关（read_file / write_file / edit_file / glob / grep / execute），`.conf/system.json` 单一事实源，设置页改开关**即时生效**（中间件每次工具调用实时读，不缓存）；
- **审批中间件**：`internal/agentkit/hooks/approve.go`——一个 `approvalMiddleware` 同时挂住同步（`WrapInvokableToolCall`）与流式（`WrapStreamableToolCall`）两个口子，第八章说"没用上的挂载点不是没用，是还没轮到"，本章轮到第二个；
- **中断-恢复闭环**：`StatefulInterrupt` 首跑中断 → checkpoint 落盘 → `approval` 事件 → 前端审批卡 → `agent/approval` 通道 → `ResumeWithParams` 把裁决精准投递给中断的那个工具——回合不崩、不重跑，从断点原地续走；
- **checkpoint 的雷拆了**：第七章第 9 节记的"列名不一致、gob 字节"两条本章全部销账（`Create`→`Save` upsert、`CheckpointID` 主键对齐、`First` 替代 `Find`、`schema.Register` 注册自定义类型）；
- **拒绝也是信息**：拒绝理由作为工具结果（字符串，不是 error）喂回模型，模型拿到的是"用户不让我干这个，原因是 X"，下一步自己改口；
- **事件协议扩充**：`approval` 事件 + `ContentItem` 的 `approval` 类型 + 前端审批卡；续跑轮与首轮共用同一套事件消费逻辑，同气泡归并（追加 + 去重）。


2. 指导思想：把"权限与安全"那章压成四条原则

动手前重读了那篇 Claude Code 源码分析的"权限与安全"章。这一章的信息量比 Hooks 那章还大——七层防御、五种权限模式、规则解析器、tree-sitter AST、23 项静态检查、沙箱、路径边界——但绝大部分是 Claude Code 作为"在用户真机上跑任意命令的 CLI"才需要的重量。taie 是桌面单用户应用，攻击面不同，照抄实现没有意义；能抄的是思想。整章可以压成四条跨规模成立的原则：

1. **默认安全，fail-closed**。不理解的结构一律不信任，读不到的配置一律当危险处理。Claude Code 的 tree-sitter 设计注释写得直白："we never interpret structure we don't understand"——解析不了就交给人；权限决策链的兜底 Step 3 是 `passthrough → ask`：所有自动化层都定不下来，最后落到人。taie 的对应物在 `needsApproval` 第一行就成立了：配置读不到，清单内工具一律审批，模式裁决根本没有出场机会；
2. **模式管策略，规则管精调**。权限模式（default / plan / bypassPermissions……）回答"默认问不问"这个全局问题，规则（`Bash(npm test:*)`）回答"哪些具体操作放行"这个局部问题，两层各管各的。taie 的对应物是三种工作模式 + 六个工具开关——开关是整工具粒度的"规则"，粗，但结构同构：模式在开关之上裁决；
3. **中断是一等公民，不是异常**。`ask` 的本质是把回合挂起来等人类输入，这时状态必须可保存、可恢复——Claude Code 的 plan 模式记住 `prePlanMode`、权限请求能在协调器与子 Agent 之间转发，都是同一个思想：等人不等于死机。taie 的对应物是 `StatefulInterrupt` + checkpoint + `ResumeWithParams`，本章的主体工程量都在这里；
4. **拒绝也是信息**。第八章讲过的"错误是信息，不是异常"在权限场景的续篇：拒绝不能让回合崩掉，要把"为什么被拒"喂回模型让它改口。Claude Code 把拒绝详情喂给模型、给 PermissionDenied Hook 发事件；taie 的对应物是把拒绝理由作为工具结果字符串喂回去。

对照关系如下：

| Claude Code 的机制 | taie 的对应物 |
| --- | --- |
| 权限模式 default / plan / bypassPermissions | `ModeManual` / `ModePlan` / `ModeAuto` |
| 工具级 allow 规则（Read、Glob 默认放行） | `PermissionSetting` 六个布尔开关（工具粒度） |
| deny 规则优先于 bypass 模式；安全检查 bypass-immune | fail-closed：读不到配置一律审批，模式裁决排在它后面 |
| 决策链兜底 Step 3：passthrough → ask（问人） | `needsApproval` 的 default 分支 + error → true |
| PreToolUse 拦截 + 交互式确认对话框 | `WrapToolCall` 中间件 + `StatefulInterrupt` |
| 回合挂起可恢复（checkpoint / plan 审查后续跑） | `CheckPointStore` + `CheckPointID(sessionID)` + `ResumeWithParams` |
| 确认对话框三源竞速（Hook / 分类器 / 人），人类意图优先 | 审批卡只有一个决定者：用户。没有分类器可竞速——桌面单用户场景，人就是最快的分类器 |
| 拒绝详情喂回模型（exit code 2 的思想） | 拒绝理由作为 tool_result 字符串喂回 |
| 设置改动即时生效（每次决策实时读配置） | 每次工具调用实时 `GetMode` / `GetPermission` |

数量上诚实对比：Claude Code 七层防御，taie 本章建成的是其中两层的穷人版——"权限模式 + 规则"（3 模式 6 开关）和"用户确认"（审批卡），外加工具级安全的挂载点地基（第八章铺的 `WrapInvokableToolCall`）。Bash AST、路径边界、沙箱、危险文件清单都还没有——欠的层在第 7 节如实列账，不是不做，是排队。


3. 权限模型：三种模式、六个开关、一条 fail-closed 底线

3.1 数据模型与决策表

权限模型全部住在一个文件里（`internal/po/system.go`），没有独立的规则引擎：

```go
// internal/po/system.go
const (
    ModeManual = "manual" // 手动：按权限开关，关=审批
    ModePlan   = "plan"   // 计划：只读放行，写/执行必须审批
    ModeAuto   = "auto"   // 自动：全部放行，减少询问
)

// PermissionSetting agent 内置工具的授权开关，key 与工具名一一对应。
type PermissionSetting struct {
    ReadFile  bool `json:"read_file"`
    WriteFile bool `json:"write_file"`
    EditFile  bool `json:"edit_file"`
    Glob      bool `json:"glob"`
    Grep      bool `json:"grep"`
    Execute   bool `json:"execute"`
}
```

判定逻辑 `needsApproval` 是整个权限系统唯一的决策点，五步，顺序即语义：

```go
// internal/agentkit/hooks/approve.go
func (m *approvalMiddleware) needsApproval(name string) bool {
    if !po.IsPermissionTool(name) {
        return false // web_search / write_todos / task / ls 等不受权限管辖
    }
    mode, err := m.repo.GetMode()
    if err != nil {
        return true // fail-closed：配置读不到，清单内一律审批
    }
    switch mode {
    case po.ModeAuto:
        return false
    case po.ModePlan:
        return po.IsWriteTool(name) // write_file / edit_file / execute
    default: // manual
        perm, err := m.repo.GetPermission()
        if err != nil {
            return true // 同上，宁可多问
        }
        allowed, ok := perm.Lookup(name)
        if !ok {
            return false
        }
        return !allowed
    }
}
```

画成决策表：

| 条件 | 判定 |
| --- | --- |
| 工具不在六工具清单内 | 放行 |
| 配置读不到（任何一步出错） | **审批**（fail-closed，优先于一切模式） |
| auto | 放行 |
| plan 且是写/执行类 | 审批 |
| plan 且是读类 | 放行 |
| manual 且开关开 | 放行 |
| manual 且开关关 | 审批 |

出厂默认（`.conf/system.json`）是 `mode: "manual"` + 六个开关全 `false`——**每个清单内工具都要审批**。这是刻意的：Claude Code 的 default 模式说"未知的操作一律询问用户"，taie 的出厂态把这句话推到极致——连 read_file 都先问一句。用户把开关逐个打开，才逐步接近 Claude Code default 模式的体验；plan 模式对应它的 plan 模式（写类必审、读类放行）；auto 对应 bypassPermissions——但注意，Claude Code 的 bypass 模式仍受 deny 规则和 bypass-immune 安全检查约束，taie 的 auto 目前是真·全放行，这层差距在第 7 节记账。

3.2 fail-closed 放在哪一层

值得单独说的是 fail-closed 的位置。`needsApproval` 里两次 `err != nil → return true` 都排在模式 switch **之前**——"配置坏了"的优先级高于"用户选了什么模式"。这抄的是 Claude Code 源码里那条最关键的检查顺序：deny 规则和安全检查排在 bypassPermissions 之前，"先检查安全路径，然后才检查 bypass"——宽松模式只有通过了更严格的关卡才有资格生效。taie 的规模用不上 deny 规则，但"出错时模式说了不算"这条次序原样保留：system.json 被手滑删了、JSON 被改坏了，结果不是全部放行（fail-open），而是全部审批。

反面教材是自己：`GetMode` 读到空字符串时返回的错误文案是"模式设置被破坏"，而前端设置页的兜底是 `cfg.mode === 'auto' || cfg.mode === 'plan' ? cfg.mode : 'manual'`——前后端对"坏数据"的处理方向一致（都往保守倒），但一处报错一处静默，风格不统一，记入遗留。

3.3 配置即数据：每次工具调用实时读

中间件对 mode / 开关**不做任何缓存**，每次工具调用都从 repo 现读：

```go
// internal/agentkit/hooks/approve.go —— 中间件无状态的原因写在结构体注释里：
// 无状态：同一批实例挂在根 agent 和所有 task 子代理上、跨会话共享，
// 权限判定所需的 mode/开关每次工具调用实时从 repo 读（system.json 很小，
// Save 是 tmp+rename 原子替换，读安全；设置页改开关即时生效）。
```

这也是从 Claude Code 抄的：它的权限决策每次都遍历 `PERMISSION_RULE_SOURCES` 收集规则，而不是启动时快照一次——所以改 settings.json 不用重启。taie 的对应收益更直观：设置页拨一个开关，下一声工具调用立刻按新规矩来，中间件实例（第八章埋的 entry 缓存复用）完全不知情。

依赖方向照旧：`PermissionRepo` 接口定义在 hooks 包、实现在 data 包（`data/permission.go`），wire 注入——和 `UsageRepo` 同款。data → agentkit 单向，hooks 依然一行都不 import data。

```go
// internal/agentkit/hooks/approve.go
type PermissionRepo interface {
    GetMode() (string, error)
    GetPermission() (*po.PermissionSetting, error)
}
```


4. 中断与恢复：等人批准是一个状态机，不是一个回调

这是本章的主体。先讲清楚为什么难：审批不是"弹个框、阻塞等返回"——Runner 是单线程事件泵，弹框阻塞的是整个会话；也不是"回调里继续跑"——用户裁决可能发生在五分钟之后、甚至应用重启之后。唯一的正解是把"等人"建模成**状态机的暂停**：首跑在工具执行前停下、完整状态落盘；裁决到达后从落盘状态恢复，把裁决投递给停下的那个点，继续跑。eino adk 的 `StatefulInterrupt` + `ResumeWithParams` 提供了这套机制，taie 做的是把它接进事件协议和前端。

4.1 首跑即中断

`WrapInvokableToolCall` 在"工具即将执行"的时刻被回调。needsApproval 判定要审批时，不执行工具，而是发起中断：

```go
// internal/agentkit/hooks/approve.go（同步版；流式版状态机完全同构）
wasInterrupted, _, storedArgs := tool.GetInterruptState[string](ctx)
if !wasInterrupted {
    // 首跑：发起中断。整个 agent 在工具执行前停下，runner 落 checkpoint，
    // 事件流以 Action.Interrupted 收口，前端据此弹审批卡片
    return "", tool.StatefulInterrupt(ctx, &ApprovalInfo{
        ToolName:        tCtx.Name,
        ArgumentsInJSON: args,
    }, args)
}
```

两个细节决定这套机制好不好用：

- **`ApprovalInfo` 带着原始入参 JSON**。中断时把 args 原样存进中断信息，续跑时用存档执行真工具，**不依赖模型重发**。如果依赖模型重发，恢复轮模型完全可能给出不同的参数——你批准的是"写 /tmp/a.txt"，实际执行的可能是"写 ~/.zshrc"，审批就白批了。存档入参让"批什么"和"跑什么"严格同一；
- **中断信息就是用户可见的审批请求**。`ToolName` + `ArgumentsInJSON` 原样穿过事件协议到达前端审批卡——中间件不另造一份"给前端的 DTO"，一份两用。

4.2 checkpoint：挂起即落盘（顺手拆雷）

中断能跨请求恢复的前提是状态落了盘。Runner 配置加一行：

```go
// internal/agentkit/chatagent.go
// 中断/恢复的定位键：不带走就没有 checkpoint，审批无从谈起
adk.WithCheckPointID(checkpointID(sessionID)),

// checkpointID 用会话 ID 作 checkpoint 键：一次会话同时只有一个挂起中断，
// 同会话下一轮 Run 的 Set（upsert）会自然覆盖。
func checkpointID(sessionID uint) string {
    return strconv.FormatUint(uint64(sessionID), 10)
}
```

键的选取是设计决策：用 sessionID 而不是随机 ID，一是**跨重启稳定**（重启后从会话 ID 能重新算出同一个键），二是天然去重（`runMu` 串行化保证一次会话同时只有一个挂起中断，下一轮 Run 的 `Set` upsert 覆盖旧的，不留垃圾行）。

第二个前提暴露了第七章埋的雷：checkpoint 表的列名和仓库行为都对不上中断/恢复的要求。本章一并拆掉：

```go
// internal/po/checkpoint.go —— 列名对齐：原来字段叫 ID、gorm 默认列 "id"，
// 与 CheckPointStore 语义对不上，改名并显式指定列
type Checkpoint struct {
    CheckpointID string    `gorm:"column:checkpoint_id;primaryKey"`
    CreatedAt    time.Time
    UpdatedAt    time.Time
    SessionID    uint64    `gorm:"index;comment:归属会话ID"`
    SnapshotJSON []byte
}

// internal/agentkit/workspace/checkpoint.go —— Create 改 Save：
// 同会话第二次中断时 Create 会撞主键，Save（gorm upsert）自然覆盖
func (c *Cpstore) Set(ctx context.Context, checkpointId string, checkpoint []byte) error {
    ...
    return c.repo.Save(ctx, &po.Checkpoint{CheckpointID: checkpointId, SnapshotJSON: checkpoint})
}

// internal/data/checkpoint.go —— Find 换 First：
// Find 查不到不报错，无法区分"不存在"和"出错"，必须用 First

```

三条改动对应第七章第 9 节记的账：列名不一致（改字段名 + 显式列名）、重复写入（Create → Save）、查询语义（Find → First）。第七章的账销一半，另一半（gob 字节）在下一节。

4.3 gob 注册：延迟引爆的地雷怎么排

checkpoint 是 gob 编码。`ApprovalInfo` 和 `ApprovalResult` 是要进 checkpoint 的自定义类型，gob 对接口值的解码需要注册具体类型——而且这颗雷的引信是**延迟**的：

```go
// internal/agentkit/hooks/approve.go
func init() {
    // checkpoint 是 gob 编码：进 checkpoint 的自定义类型必须注册，
    // 否则不在当下报错，而是 Resume 解码时才失败（官方 approval_wrapper 同款）
    schema.Register[*ApprovalInfo]()
    schema.Register[*ApprovalResult]()
}
```

"不在当下报错"是最阴险的失败模式：注册漏了，首跑、中断、落盘全部正常，前端卡片都弹出来了——直到用户按下批准按钮，Resume 解码 checkpoint 时才炸。到时候用户看到的是"恢复执行失败"，而病根在几十分钟前的一个 init 里。第七章记的"gob 字节"雷指的就是这一类问题，本章用两行 `schema.Register` 排掉，第七章的账全额销清。

4.4 事件泵共用与中断识别

Runner 的消费循环抽出成 `pump`，首轮 Run 与审批续跑 Resume 共用。新增的分支只有一个：

```go
// internal/agentkit/chatagent.go
// 审批中断：工具执行前停下，发 approval 事件后本轮结束
//（中断事件是该次迭代的最后一个事件，之后 Next() 即结束）。
// 判断只看 Action，不要依赖该事件上的 Output（可能为 nil）。
if agev.Action != nil && agev.Action.Interrupted != nil {
    name, args, icID, ok := approvalInterrupt(agev.Action.Interrupted)
    if !ok {
        return onEvent(events.Error("执行被中断")) // 非审批类中断，v1 统一按错误处理
    }
    // 挂起轮不落库、不发 done：回合等审批续跑后继续
    return em.Approval(name, args, icID)
}
```

"挂起轮不落库、不发 done"是协议层面的关键决策：这一轮**没有结束**，只是暂停。不落库——assistant 消息等续跑轮的 done 一起收；不发 done——前端不会把气泡置成 completed，生成态由 `pauseForApproval`（5.3）管理。中断的识别只看 `Action.Interrupted`，不碰 `Output`——中断事件上 Output 可能是 nil，这是 eino 的接口现实，注释里钉死防后人。

从中断链里挑出审批中断点的逻辑：

```go
// internal/agentkit/chatagent.go
// approvalInterrupt 从中断链里挑出审批中断点（Info 为 *hooks.ApprovalInfo 的那个，
// 多个命中时优先 IsRootCause），其 ID 是 ResumeWithParams 的定位键。
func approvalInterrupt(info *adk.InterruptInfo) (toolName, argsJSON, interruptID string, ok bool) {
    for _, ic := range info.InterruptContexts {
        ai, is := ic.Info.(*hooks.ApprovalInfo)
        if !is {
            continue
        }
        if !ok || ic.IsRootCause {
            toolName, argsJSON, interruptID, ok = ai.ToolName, ai.ArgumentsInJSON, ic.ID, true
            if ic.IsRootCause {
                break
            }
        }
    }
    return
}
```

4.5 续跑：Targets 精准投递

用户裁决后，前端通过 `agent/approval` 通道发回 `{session_id, interrupt_id, approved, reason}`，Go 侧从 checkpoint 恢复：

```go
// internal/agentkit/chatagent.go
func (c *ChatAgent) Resume(ctx context.Context, sessionID uint, b *provider.BuildParams,
    interruptID string, approved bool, reason string, onEvent func(events.Event) error) error {

    e, err := c.getEntry(ctx, sessionID, b) // 同 entry 复用；模型配置取会话快照
    ...
    // 与 Runner 同款串行化：entry 里的 agent 与 middleware 实例被同会话共享
    e.runMu.Lock()
    defer e.runMu.Unlock()
    res := &hooks.ApprovalResult{Approved: approved}
    if !approved && reason != "" {
        res.DisapproveReason = &reason
    }
    ...
    agevs, err := runner.ResumeWithParams(ctx, checkpointID(sessionID), &adk.ResumeParams{
        // key 必须是 approval 事件里原样回传的 interrupt_id
        Targets: map[string]any{interruptID: res},
    }, adk.WithCallbacks(c.tracer))
    ...
    em := events.NewEmitter(sessionID, onEvent)
    return c.pump(ctx, sessionID, agevs, em, onEvent)
}
```

三个工程要点：entry 复用与 `runMu` 串行化和 Runner 完全同款（第八章的并发地基直接受益）；模型配置走会话快照（`sess.ApiKey / BaseURL / ModelName`），中断前用哪个模型、续跑还是哪个模型；`Targets` 以 `interrupt_id` 为键精准投递——裁决只给停下的那个工具调用点，不是"从头再跑一遍"。

续跑后，包装的 endpoint 再次执行，进入状态机的另一半：

```go
// internal/agentkit/hooks/approve.go
// 续跑：ResumeWithParams.Targets 以 interrupt_id 投递的裁决出现在这里
isTarget, hasData, result := tool.GetResumeContext[*ApprovalResult](ctx)
if isTarget && hasData {
    if result.Approved {
        // 批准：用存下的原始入参执行真工具
        return endpoint(ctx, storedArgs, opts...)
    }
    // 拒绝：把理由作为工具结果（字符串而非 error）喂回模型，模型会改口
    if result.DisapproveReason != nil {
        return fmt.Sprintf("工具 %s 被用户拒绝，原因：%s", tCtx.Name, *result.DisapproveReason), nil
    }
    return fmt.Sprintf("工具 %s 被用户拒绝", tCtx.Name), nil
}
```

拒绝分支值得多看一眼：返回的是**字符串**，不是 error。error 会被 safeTool 包成失败、触发模型的"工具失败了"叙事；字符串工具结果则是平静地告诉模型"用户拒绝了，理由是 X"——模型在下一轮自然改口换方案。这是第八章原则 4（错误是信息）在权限场景的精确复刻。

4.6 同批多工具：连续审批

模型一次输出多个工具调用、且多个都要审批时，中断链上有多个中断点。`Resume` 只投递一个 Target，状态机里对应地有两个分支：

```go
// internal/agentkit/hooks/approve.go
// 非本轮恢复目标（同批多工具先后审批，只批了别的那个）：
// 原样再中断保持状态，等下一轮 ResumeWithParams 指到它
isTarget, _, _ = tool.GetResumeContext[any](ctx)
if !isTarget {
    return "", tool.StatefulInterrupt(ctx, &ApprovalInfo{
        ToolName:        tCtx.Name,
        ArgumentsInJSON: storedArgs,
    }, storedArgs)
}

// 是本轮目标但未携带数据（隐式恢复）：默认放行
return endpoint(ctx, storedArgs, opts...)
```

效果：批了 A，B 原样再中断、事件流再次以 `Interrupted` 收口、前端再次收到 approval 事件弹出下一张卡——连续审批在协议层表现为"approval 会话中可能再次出现"（app.go 注册通道时的注释原话），前端不需要任何额外逻辑。

但要如实记一笔：**"隐式恢复 = 放行"是一条 fail-open 通道**。Resume 目标命中但没带数据时，默认放行执行——这是 eino 的语义，taie 自己的调用方（`ApprovalWithAgent`）永远携带 `ApprovalResult`，所以当前跑不到这条分支；可它和本章 3.2 刚立完的 fail-closed 底线相逆。防御性做法是数据缺失时改为再中断或拒绝，记入遗留。

4.7 中间件次序：审批必须待在 safeTool 之内

 BuildHooks 里的注册顺序变了，且必须变：

```go
// internal/agentkit/hooks/hook.go
func BuildHooks(repo UsageRepo, perm PermissionRepo) []adk.ChatModelAgentMiddleware {
    return []adk.ChatModelAgentMiddleware{
        &safeToolMiddleware{},
        &dynamicPromptToolMiddleware{},
        // 审批中间件放在 safeTool 之内（注册序在后 = 包装更内层）：
        // StatefulInterrupt 的中断错误要经 safeTool 的 IsInterruptRerunError
        // 直通分支原样穿透，不能被它转成 "[tool error] ..." 字符串
        newApprovalMiddleware(perm),
        &usageMiddleware{repo: repo},
    }
}
```

`StatefulInterrupt` 的实现机制是"用一种特殊的控制流错误向外抛"，而 safeTool 的职责恰恰是把工具错误包装成 `[tool error]` 字符串喂回模型。如果审批中间件注册在 safeTool 之外（更外层），中断错误半路就被包成字符串，恢复链当场断裂——表现为审批卡弹出来、点批准后模型收到一句"[tool error]"然后一脸茫然。第八章给 safeTool 铺的 `IsInterruptRerunError` 直通分支（"中断不是失败，放它出去触发 rerun 逻辑"）在这里第一次救命：注册序在后 = 包装更内层，中断错误先穿过 safeTool 的直通口子原样出去。铺路兑现的又一笔。

4.8 流式同构：WrapStreamableToolCall 到岗

第八章盘点过：eino 的 9 个挂载点 taie 用了 3 个，"没用上的 6 个不是没用，是还没轮到"。本章轮到第一个——`WrapStreamableToolCall`。原因：taie 的 execute 工具配了 StreamingShell，注册的是 StreamableTool，只写 Invokable 版**拦不住它**——流式工具走的包装入口是另一个。所以审批中间件是双份实现，状态机逐行同构，仅返回类型不同（`string` vs `*schema.StreamReader[string]`）：

```go
// internal/agentkit/hooks/approve.go
// WrapStreamableToolCall 拦截流式工具。taie 配了 StreamingShell，
// execute 注册的是 StreamableTool，只写 Invokable 版拦不住它。
// 状态机与 WrapInvokableToolCall 完全同构，仅返回类型不同。
```

拒绝回执走流式出口时用 `singleChunkReader` 把整段文本包成单 chunk 只读流——协议形态服从工具形态。双份实现是重复代码，但此刻不抽公共：两处状态机 60 行，抽象层的收益暂时是负的。等第三个变体出现（如果出现）再谈收敛。


5. 事件协议与前端：一张卡、一条通道、一套消费逻辑

5.1 approval 事件

事件协议新增一个 kind，与 delta / tool_call / tool_result 同级：

```go
// internal/pkg/events/event.go
EventApproval EventKind = "approval" // 工具等待审批：content=[approval]，
                                     // extra.interrupt_id 必须原样回传 agent/approval
```

对应的 `ContentItem`：`Type: "approval"`、`Name` 为工具名、`Result` 为入参 JSON、`Status: loading`、`Extra["interrupt_id"]` 为续跑定位键。`Emitter.Approval` 把卡片项追加进内容序列并下发——注意只追加、不收口：这一轮没有 done，序列的最终态要等续跑轮。

5.2 agent/approval：协议对称的第二条通道

```go
// internal/app/app.go
// 注册审批回调通道，协议与 agent/chat 对称：
// 前端收到 approval 事件弹卡片，用户裁决后发一条 {"session_id","interrupt_id","approved","reason"}，
// Go 从 checkpoint 续跑并回推同一套事件，直到 done/error/approval(多工具连续审批)。
wailsApp.HandleStream("agent/approval", func(c *application.StreamConn) { ... })
```

为什么是独立通道而不是复用 agent/chat 连接？因为挂起轮的连接已经关了（`pauseForApproval` 关闭 socket，见下节），Wails 的 HandleStream 按连接生效；新连接意味着干净的协议边界——一个连接负责一轮。真正的收益在另一头：**Resume 回推的事件流（delta / tool_call / tool_result / done / 乃至下一个 approval）与首轮完全一致**，前端的 `handleEvent` 一行不改、两个通道共用。协议的对称性直接兑换成了前端代码的复用率。

5.3 挂起不是结束：pauseForApproval vs finish

前端状态机的核心是分清两种"停"：

```tsx
// frontend/src/components/aichat/provider/index.tsx
/** 审批暂停——关连接、generate=false，但不动气泡状态、不清挂起审批
    （回合没结束，只是挂起等裁决） */
const pauseForApproval = useCallback(() => { ... }, [])

/** 真正收口：清缓冲、关连接、清挂起审批、复位状态 */
const finish = useCallback((mark?: string) => {
    ...
    // 任何收口都终结挂起审批（停止/断连/发新消息 = 放弃裁决）
    pendingApprovalRef.current = null;
    setPendingApproval(null);
    ...
}, [])
```

`finish` 是终点：停止生成、连接异常断开、用户直接发新消息——任何路径都等于放弃裁决（新消息会让下一轮 Run upsert 覆盖 checkpoint，旧的挂起自然作废，不会留脏状态）。`pauseForApproval` 是暂停：气泡状态原样、挂起审批原样，只是连接关了、输入解锁（generate=false，用户还能打字，但发消息即放弃裁决）。approval 事件到达时的处理顺序：追加卡片 → 记录 `pendingApproval`（state 供渲染 + ref 供闭包立即读到最新值）→ `pauseForApproval`。

5.4 审批卡：谁有资格按下按钮

```tsx
// frontend/src/components/aichat/chatmessage/approvalCard/index.tsx
/** approval 审批卡：工具执行前等待人工裁决。
    仅当"本卡片的 interrupt_id == 当前挂起审批 && 不在生成中"时可交互；
    裁决后 status 由 provider 置 completed(批准)/failed(拒绝)，转为结果态。 */
const active = !!pendingApproval
    && pendingApproval.interruptId === interruptId && !generate;
```

可交互条件是双重锁：interrupt_id 必须匹配当前挂起审批（连续审批时只有最新一张卡活着，历史卡片自动转结果态），且不在生成中（续跑期间按钮全部失效，防止重复裁决）。拒绝流程多一步：点"拒绝"先展开理由输入框，理由可选、会告知 agent——4.5 的拒绝通道在 UI 上的对应物。裁决后 provider 把卡片 status 置 completed / failed，按钮消失，卡片变成一张结果记录，留在对话流里可回溯。

`decideApproval` 里还有一个容易忽视的细节：卡片落定（改 status）发生在**发续跑请求之前**——先冻结这张卡的状态，再开连接。若反过来，续跑轮的事件和本地的裁决状态更新会竞争同一份 content。

顺带一提，历史遗留的 `ToolCallCard`（第八章之前内联在 chatmessage 里）本次提取成独立组件并换上 Card + Badge 的统一样式——审批卡和工具卡在视觉上是同一个语言：色点表状态，卡片表边界。

5.5 续跑轮的 done：追加 + 去重

done 事件在续跑轮的语义变了。首轮 done 的服务端 content 是整轮重组的完整序列，前端整体替换（消除流式归并漂移）；续跑轮的服务端只重组了**续跑段**的内容，整体替换会把审批前的正文和卡片全部抹掉。所以有了 `resumingRef`：

```tsx
// frontend/src/components/aichat/provider/index.tsx
if (resumingRef.current) {
    // 审批续跑轮的 done 是"追加 + 去重"——服务端只重组了续跑段内容，
    // 整体替换会抹掉审批前的正文与卡片；按 type:call_id 去重防止
    // 服务端把已完成的 tool_result 再发一遍
    resumingRef.current = false;
    ... // 追加 fresh items，已见过的 call_id 跳过
} else {
    ... // 原逻辑：整体替换 + sameContent 消除收口闪动
}
```

这里兑现了前端事件归并一直采用的"单气泡"设计（工具卡与正文同住一个气泡、按 call_id 互相归位）：审批前后所有内容都归并在同一个气泡里，`tool_result` 归位命中的就是中断前那张工具卡——从用户视角看，整个"调用 → 审批 → 执行 → 回执"是连续的一段对话，没有任何断点感。断点只存在于状态机内部。


6. 设置页与装配：权限开关是一等公民设置

设置页从"摆设"升级为权限系统的控制台：工作模式下拉（手动 / 计划 / 自动）、六个工具开关，加上原有语言、通知项。实现模式是**即时生效型 UI**：每次变更把当前快照加 patch 整体写回 system.json，保存失败只提示不回滚，下次进入设置页以后端为准。

```tsx
// frontend/src/components/setting/system/index.tsx
// 即时生效型 UI：每次变更把当前快照加 patch 整体写回 system.json；
// 保存失败只提示不回滚，下次进入设置页会以后端为准
const saveConfig = (patch: Partial<SystemConfig>) => {
    const config: SystemConfig = { language, mode, fontSize, notifications, permissions, ...patch }
    SystemServices.Update({ config }).catch(err => Toast.error(`保存系统设置失败：${String(err)}`))
}
```

链路上新增的服务与装配：`SystemServices` / `SystemRepo`（system.json 的读写，wire 注册 `NewSystemRepo` / `NewSystemServices`）、`data.NewPermissionRepo`（实现 hooks 的 `PermissionRepo`）、`BuildHooks` 增加第二参数、app.go 注册 `agent/approval` 通道并挂载 SystemServices。每一处都是既有装配模式的照抄——这一章没有任何新的架构机制，全部是第八章搭好的轨道上跑新车。

要记一笔账：工具开关清单在前端（`permissitionItems`）和后端（`PermissionSetting.Lookup`）各维护一份，key 必须一字不差——加一个清单内工具要同步改两处。SystemConfig 本体有 bindings 生成兜底，开关的 UI 清单没有。数量少（6 项）时不痛，先记着。


7. 诚实对比：欠的层与还的顺序

把 taie 现在的权限体系放回 Claude Code 的七层框架里量一量：

| Claude Code 的层 | taie 现状 |
| --- | --- |
| L1 工作区信任确认 | 不适用（桌面单用户，无"clone 陌生仓库"场景） |
| L2 权限模式 | ✅ 3 模式（manual / plan / auto） |
| L3 权限规则匹配 | ◑ 半层：6 个整工具开关，无内容级规则（无前缀 / 通配符 / 精确匹配，无 deny 清单） |
| L4 Bash 多层安全（AST + 23 项检查） | ❌ 无——execute 过了审批就是直通 shell |
| L5 工具级安全（validateInput / 危险文件） | ◑ 挂载点在（WrapToolCall），检查逻辑未做 |
| L6 沙箱与隔离 | ❌ 无 |
| L7 用户确认 | ✅ 审批卡（但见第 8 节新账第 1 条：卡上没有入参） |

排序上的一点判断：下一道最值的防线不是沙箱也不是 AST，而是 **execute 的命令级规则**（deny 清单 + 前缀 allow）。理由是清单里只有 execute 能"跑任意命令"——write_file 至少限定在写文件，execute 审批通过之后的每一秒都在规则之外。Claude Code 给 Bash 单独建了整套多层验证，攻击面在哪、防线就该先长在哪。AST 解析、路径边界、危险文件清单（`.zshrc` / `.gitconfig` 那一类）次之；沙箱在桌面单机场景边际收益暂时排最后。

还有一层是免费拿到的：Prompt Injection 防御的结构化消息部分（模型能区分用户输入和 tool_result）由 eino 的消息结构天然提供——不是 taie 做得好，是站在框架肩膀上顺便有。system-reminder 伪造检测、注入告警那些主动防御，等真实场景出现了再议。


8. 铺路清单与遗留清单

**本章铺的路**

| 铺设物 | 等谁 |
| --- | --- |
| approval 事件 + 审批卡协议（ContentItem / interrupt_id 透传） | MCP 工具接入后的第三方工具审批——同一中间件、同一协议、零改动 |
| `PermissionRepo` 接口（hooks 定义 / data 实现） | 内容级规则引擎（deny 清单、命令前缀规则）：hooks 不动，data 换实现 |
| `CheckPointID(sessionID)` 稳定键 + Save upsert | 多轮连续中断、长任务断点续跑 |
| 拒绝理由通道（UI → 协议 → 模型上下文） | 用户偏好记忆："它总拒绝我 rm -rf"可以沉淀成提示词 |
| `WrapStreamableToolCall` 首个住户 | 流式工具的后续横切（审计、限流） |

**销账**

- 第七章第 9 节的 checkpoint 雷**全额销清**：列名不一致（`CheckpointID` 主键 + 显式列名）、重复写入（`Create` → `Save` upsert）、查询语义（`First` 替代 `Find`）、gob 字节（`schema.Register` 两行）。

**新账**

1. **审批卡是盲盒**：`ArgumentsInJSON` 一路下发了（ContentItem.Result 字段），`ApprovalCard` 却没有渲染它——用户看到的是"工具 write_file 等待审批"，看不到它要写哪个文件、execute 要跑哪条命令。Claude Code 的确认对话框有 Permission Explainer（Haiku 生成的解释 + 风险等级），taie 连原始入参都还没摆出来。下一刀该切这里，优先级最高的 UX 债；
2. **重启后前端没有恢复入口**：服务端链路是通的（checkpoint 持久化 + `CheckPointID` 稳定 + `Resume` 可跨进程），但挂起轮不落库、审批卡只活在内存里——重启等于没有卡片，也就没有裁决，checkpoint 在库里等一个不会来的 Resume（下一轮发消息会 upsert 覆盖，不会脏，但那次挂起作废）。差一块"从历史恢复挂起审批"的前端逻辑；
3. **auto 是真·全放行**：Claude Code 的 bypassPermissions 仍受 deny 规则与 bypass-immune 检查约束，taie 的 auto 连清单内的 write/execute 都直接放行——设置页文案"减少询问你的意见"实际语义是"取消询问"。在 deny 清单落地前，auto 的安全假设就是"你信这个模型"，文案值得改诚实；
4. **隐式恢复 = 放行**（见 4.6）：一条 fail-open 通道躺在 fail-closed 的体系里。当前调用方永远带数据，跑不到；但语义相逆，防御性收口（缺数据改再中断）值得做；
5. **decideApproval 的注释超前了**：注释说"idAdoptedRef 置 true 不再采纳新 id"，代码里没有这一行。现在不出事是因为前端归并认的是 `activeIdRef` 而非事件里的 msg.id——第八章新账第 4 条（注释比代码超前）的同款病例，地图和地形必须有一个是对的；
6. **evictIdleLocked 数据竞争**（第八章新账第 1 条）**连续第二次跳票**。本章在同一个文件里进进出出了一整天，愣是没修——账面利息继续涨，下一章真的第一件事修它；
7. **沿用未动**：AgentRepo 的 `AppendTokenUsage` 死代码、ChatSession 快照向前端泄露 apiKey、`permissitionItems`（拼写家族新丁：permissition；emiter.go 里 emitter 已改名 Emitter、文件名仍姓 e，家族半洗白）、`buildMessage` 硬编码 40 条历史——索引见第八章第 11 节。
