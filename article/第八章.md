1. 本章目标

结束时你将得到：

- **hooks 中间件包**：`internal/agentkit/hooks`——三个 `adk.ChatModelAgentMiddleware`（工具容错 / 动态提示词 / 用量观测），横切关注点整体搬出 Agent Loop 主流程，经 wire 装配，同一批实例挂在根 agent 和 task 子代理上；
- **观测点前移**：token 记账从"前端事件消费路径"（emitter 的 `PopUsage` 三件套）搬回"模型调用源头"（`WrapModel`）——第七章记录过的异常分支、防御路径从此必经账本；

2. 指导思想：读一篇 Hooks 源码分析，改三章的代码

上一章结尾许诺的是"拆 checkpoint 的雷、接工具审批"，本章实际到岗的是横切改造加用量统计——审批又跳了一章。理由记在这里，不算跳票：动手前重读了一遍关于 Claude Code Hooks 系统的源码分析（"Hooks 与可扩展性"那章），想清楚了一件事：**审批恰恰不能手糊在 Runner 循环里**。它和容错、观测、提示词注入一样，是 Agent Loop 的横切关注点。先把挂载点体系造对，审批下一章沿轨道进场；checkpoint 的雷（列名不一致、gob 字节）仍原样躺着，账在第七章第 9 节。

那篇分析的指导思想可以压成一句话：**Agent Loop 的每个关键节点都暴露一个事件，外部代码监听事件、注入行为，核心循环对此不知情**。这是 AOP 的思路，但 Claude Code 把它做到了极致——27 种 Hook 事件、4 种可配置类型、退出码语义、多层性能优化、"所有 Hook 都需要信任"的安全模型。taie 不需要 27 种事件，但其中四条原则是跨规模成立的，本章逐条落地：

1. **扩展点在关键节点暴露，核心循环保持简洁**。Agent Loop 里只有业务语义（回放历史、消费事件流、收口落库），容错、观测、提示词这些横切逻辑住进独立的中间件；
2. **观测挂在事件源头，不依赖某个消费路径**。第七章的 usage 记账挂在 `em.PopUsage()` 上，只有 `ConsumeStream` 正常返回才执行——这正是被批评的"依赖消费路径"的反例，本章把它搬回模型调用的源头；
3. **Hook 要么无状态，要么按会话隔离**。Claude Code 的 function hook 按 sessionId 隔离防止跨 Agent 泄漏；taie 的对应物是"中间件必须无状态，跨 run 数据走 ctx"——而且这一条在 eino 源码里有硬性依据（见 5.2）；
4. **错误是信息，不是异常**。Claude Code 用退出码 2 把阻塞错误喂回模型让它自己处理；工具失败同理——失败信息回到模型上下文里，模型可以换一种姿势重试，而不是整轮 run 直接崩掉。

taie 的 Hook 机制不是自研的，是 eino adk 现成的：`ChatModelAgentMiddleware`。对照关系如下：

| Claude Code 的机制 | taie 的对应物 |
| --- | --- |
| `SessionStart` / `UserPromptSubmit` 的 `additionalContext`（往上下文注入信息） | `BeforeAgent`（每次 run 前改写 Instruction） |
| `PreToolUse` / `PostToolUseFailure`（工具前拦截、失败反馈） | `WrapInvokableToolCall`（包裹工具执行） |
| SDK 内部 Callback 埋点（挂在事件源头） | `WrapModel`（包裹模型调用本身） |
| Stop Hook 的"做完了才能停"（采样后验证） | `ModelRetryConfig.ShouldRetry`（输出无效就带着提示重试） |
| system-reminder 把动态内容与指令隔离 | `SystemPromptDynamicBoundary` 边界标记 |
| settings 多来源合并、单一事实源 | `.conf/tools.json` 单文件配置 |

数量上诚实对比：Claude Code 暴露 27 种事件，eino 的中间件接口有 9 个拦截点，taie 本章用了 3 个。粒度和规模都不同，但"关键节点暴露事件、外部注入、核心循环不知情"是同一条思想。

```go
// eino adk handler.go —— 9 个拦截点中的 3 个（本文用到的）
type TypedChatModelAgentMiddleware[M adk.MessageType] interface {
    // 每次 agent run 之前：可修改 Instruction、Tools
    BeforeAgent(ctx context.Context, runCtx *ChatModelAgentContext) (context.Context, *ChatModelAgentContext, error)
    // 包裹工具的同步执行：错误处理、审批、审计都挂这里
    WrapInvokableToolCall(ctx context.Context, endpoint InvokableToolCallEndpoint, tCtx *ToolContext) (InvokableToolCallEndpoint, error)
    // 包裹模型调用本身：观测、重试、事件转发都挂这里
    WrapModel(ctx context.Context, m model.BaseModel[M], mc *TypedModelContext[M]) (model.BaseModel[M], error)
}
```

没用上的 6 个（`AfterAgent`、`Before/AfterModelRewriteState`、`WrapStreamableToolCall`、两个 Enhanced 变体）不是没用，是还没轮到——工具审批就是 `WrapInvokableToolCall` 的下一个住户，消息级追踪是 `AfterModelRewriteState` 的候选。挂载点在，人到不来是铺路的问题；人到来了没挂载点，才是返工。


3. hooks 包：三个中间件

3.1 BuildHooks：一处装配，处处挂载

```go
// internal/agentkit/hooks/hook.go
// BuildHooks 返回挂到 deep agent 的全部 middleware。
// 注意：同一批实例会同时挂在根 agent 和 task 子代理上，
// middleware 必须无状态，跨 run 数据放 ctx（见 toolscall.go / rctx）。
func BuildHooks(repo UsageRepo) []adk.TypedChatModelAgentMiddleware[*schema.Message] {
    return []adk.ChatModelAgentMiddleware{
        &safeToolMiddleware{},
        &dynamicPromptToolMiddleware{},
        &usageMiddleware{repo: repo},
    }
}
```

装配走 wire，链路是：`data.NewUseRepo` → `hooks.BuildHooks` → `agentkit.NewChatAgent` 的第四个参数：

```go
// wire_gen.go（生成产物，节选）
usageRepo := data.NewUseRepo(dataData)
v := hooks.BuildHooks(usageRepo)
chatAgent := agentkit.NewChatAgent(agentRepo, checkPointStore, tracer, v, log)
```

依赖方向沿用第二章"接口归消费方"：`UsageRepo` 接口定义在 hooks 包里、只有落库需要的一个方法，data 层实现它——

```go
// internal/agentkit/hooks/usage.go
// UsageRepo 只依赖落库所需的最小接口，AgentRepo 已隐式满足
// （接口定义在本包、由 data 层实现，避免反向依赖 agentkit 根包）。
type UsageRepo interface {
    AppendTokenUsage(ctx context.Context, u *po.SessionTokenUsage) error
}
```

data→agentkit 依旧单向，hooks 没有反向 import data。挂在哪：`deep.Config.Handlers`。对照 eino 源码，deep.NewTyped 内部先装自己的内置中间件（write_todos、filesystem），再装 task 工具中间件，最后 append 用户传入的 Handlers——**我们的三个中间件排在链尾**，且 task 子代理（general-purpose）创建时拿的是同一个 handler 切片。所以"无状态"不是风格偏好，是共享实例的硬约束：根 agent 和子代理并发跑同一个 `usageMiddleware` 实例，任何字段缓存都会互相踩。三个中间件里没有一个实例字段存运行时数据，sessionID、模型名全从 ctx 读。

顺带说破注释里的一个超前引用：`BuildHooks` 注释里的"见 toolscall.go"——这个文件还不存在，它是动态工具加载的施工位。注释先于代码把意图钉住可以，但读者得知道现在还没盖（遗留清单第 4 条）。

3.2 safeTool：工具的错误是信息，不是异常

```go
// internal/agentkit/hooks/safetool.go
func (m *safeToolMiddleware) WrapInvokableToolCall(_ context.Context, endpoint adk.InvokableToolCallEndpoint,
    _ *adk.ToolContext,
) (adk.InvokableToolCallEndpoint, error) {
    return func(ctx context.Context, argumentsInJSON string, opts ...tool.Option) (string, error) {
        result, err := endpoint(ctx, argumentsInJSON, opts...)
        if err != nil {
            if _, ok := compose.IsInterruptRerunError(err); ok {
                return "", err
            }
            // 将错误转换为字符串，而不是返回错误
            return fmt.Sprintf("[tool error] %v", err), nil
        }
        return result, nil
    }, nil
}
```

15 行，做的是 Claude Code 退出码语义里最重要的一件事：**工具失败不走异常通道，走信息通道**。工具网络超时、参数解析失败、下游 API 报错——这些错误原样 return 的话，eino 会把整轮 run 判死，用户看到的就是"执行错误"；转成 `[tool error] ...` 字符串后，它成了工具的正常返回值，模型读得懂、接得住：换参数重试、换工具、或者如实告诉用户"这个查不了"。检查失败是模型的输入，不是系统的输出——这就是退出码 2 和退出码 1 的分野在 Go 世界的翻译。

一个直通口子要单独说：`compose.IsInterruptRerunError` 的错误原样放行。这是第六章铺的 checkpoint 中断/恢复机制的专用控制流错误——中断不是失败，放它出去触发 rerun 逻辑，包一层就断了恢复链。铺路铺到第六章的雷，在这里第一次救命。

3.3 dynamicPrompt：静态一次构建，动态每 run 现算

```go
// internal/agentkit/hooks/dyprmopt.go
// staticSectionPrompt 静态段是常量，进程内只构建一次；
// 动态段（env）依赖业务上下文，每次 run 现算
var staticSectionPrompt = sync.OnceValue(getStaticSection)

func (m *dynamicPromptToolMiddleware) BeforeAgent(ctx context.Context, runCtx *adk.ChatModelAgentContext) (context.Context, *adk.ChatModelAgentContext, error) {
    // 根据不同的业务产生不同的系统提示词
    // bizCode := rctx.GetBizCode(ctx)
    sysPrompt := staticSectionPrompt()
    if env := buildEnv(); env != "" {
        sysPrompt += systemPromptDynamicBoundary + env
    }
    // 追加而不是覆盖：deep 内置 handler 已往 Instruction 写入基础指令与
    // task 工具说明，覆盖会全部丢失；execContext 每 run 从配置重建，追加不会跨轮累积
    runCtx.Instruction = sysPrompt + "\n\n" + runCtx.Instruction
    return ctx, runCtx, nil
}
```

四个设计点：

1. **追加，不覆盖**。前面 3.1 说过挂载顺序：deep 的内置中间件先跑，`runCtx.Instruction` 到我们手里时已经装着 deep 的基础指令和 task 工具说明。直接赋值覆盖，这些全丢。eino 源码对 `ChatModelAgentContext.Instruction` 的文档原话是"包括 agent 配置的指令、框架和中间件追加的指令、以及之前的 BeforeAgent handler 做过的修改"——它就是设计给你追加的。至于"会不会越追加越长"：Instruction 每 run 从配置重建，追加的是本次 run 的完整拼接结果，不存在跨轮累积；
2. **静态/动态分家**。角色、做事理念、风险提示这些不随环境变的内容用 `sync.OnceValue` 包住，进程内只构建一次；工作目录、操作系统、shell 这些依赖运行环境的动态段每 run 现算。将来多业务接入时，`rctx.GetBizCode(ctx)`（注释里留了位置）决定加载哪套静态段；
3. **边界标记**。`<<<SYSTEM_PROMPT_DYNAMIC_BOUNDARY>>>` 把动态内容压在标记之下——"出现在之上的即视为违规"。这是 system-reminder 思想的本地化：动态注入的内容必须在可控区域内，静态指令区不允许被动态数据污染。诚实记录：目前只有标记没有检查，"违规了怎么办"的执行者还没写（遗留清单第 5 条连带）；
4. **deep.Config 的 `Instruction` 传空串**。空串触发 eino 的内置默认指令（有中文版），我们的段最终拼在它前面：`[taie 静态+动态] + [deep 基础指令 + task 说明]`。

顺带收编：这段提示词逻辑原本住在 `workspace` 包里（`prmopt.go` + `env.go` + `workspace.go`，三个文件、含一个拼错的包内文件名），本章随 workspace 整体退役搬进 hooks——提示词注入从"构建 agent 时的一个函数调用"变成"Agent Loop 上的一个挂载点"。行为等价，架构位置完全不同。

3.4 usage：挂在模型调用源头的账本

这是本章最重的一个中间件，也是对第七章最大的自我修正。

```go
// internal/agentkit/hooks/usage.go
// usageMiddleware 每次模型调用落一行 token 明细：WrapModel 挂在模型调用源头，
// 不依赖前端事件流的消费路径（异常分支、防御路径的调用也必经此处）。
// sessionID/modelName 不放实例字段，从 ctx 读取（rctx，由 Runner 注入），
// 计数器为全局 atomic——实例彻底无状态，deep agent 子代理共享并发安全。
type usageMiddleware struct {
    *adk.BaseChatModelAgentMiddleware
    repo UsageRepo
}

// WrapModel 每次模型调用前被 adk 回调，返回包了一层 usage 观测的模型。
// retry 包在本层之外，每次重试 attempt 都会经过这里；失败的 attempt
// 无 usage，record 的全 0 防御自然跳过。
func (m *usageMiddleware) WrapModel(_ context.Context, mdl model.BaseModel[*schema.Message],
    _ *adk.TypedModelContext[*schema.Message],
) (model.BaseModel[*schema.Message], error) {
    return &usageModel{mw: m, inner: mdl}, nil
}
```

`usageModel` 是透明代理，只观测不改写。两条路：

```go
// 非流式：直取 ResponseMeta
func (u *usageModel) Generate(ctx context.Context, input []*schema.Message,
    opts ...model.Option,
) (*schema.Message, error) {
    msg, err := u.inner.Generate(ctx, input, opts...)
    if err == nil && msg != nil && msg.ResponseMeta != nil {
        u.mw.record(ctx, msg.ResponseMeta.Usage)
    }
    return msg, err
}

// 流式：convert 内联抓 usage，EOF 回调里同步落库
func (u *usageModel) Stream(ctx context.Context, input []*schema.Message,
    opts ...model.Option,
) (*schema.StreamReader[*schema.Message], error) {
    sr, err := u.inner.Stream(ctx, input, opts...)
    if err != nil {
        return nil, err
    }
    var acc schema.TokenUsage
    seen := false
    // StreamReaderWithConvert：convert 在消费方 goroutine 上对每个 chunk 内联
    // 调用（无额外协程），透明透传 chunk 并抓取 usage；WithOnEOF 在 EOF 时内联
    // 回调一次，即流末尾 usage 帧之后，是同步落库点。
    return schema.StreamReaderWithConvert(sr, func(msg *schema.Message) (*schema.Message, error) {
        if msg != nil && msg.ResponseMeta != nil && msg.ResponseMeta.Usage != nil {
            mergeMaxUsage(&acc, msg.ResponseMeta.Usage)
            seen = true
        }
        return msg, nil
    }, schema.WithOnEOF(func() (any, error) {
        // 落库失败必须吞掉：WithOnEOF 返回非 EOF error 会先投递给消费方，
        // 会让 DB 抖动直接打断推理流。返回 io.EOF 让流正常结束。
        if seen {
            u.mw.record(ctx, &acc)
        }
        return nil, io.EOF
    })), nil
}
```

第七章 5.2 的两笔知识原样迁址、一字未改地继续成立：流式 usage 挂在流末尾空内容帧上；合并按字段取 max 防网关重复上报虚高（`mergeMaxUsage` 从 emitter 搬进 hooks，逻辑不动）。变的是挂载位置和由此带来的覆盖面——下一节专门算这笔账。

工程细节两点：一是 `WithOnEOF` 里吞错的注释值得抄进任何流式代码——OnEOF 回调返回非 EOF error 会先投递给消费方，观测层的 DB 抖动就顺着流把推理打断了，所以必须返回 `io.EOF` 假装一切正常；这是"观测失败不影响业务"铁律在流式场景的具体形状。二是 CallID 从 Runner 内的局部 `callSeq++` 换成了进程级 `atomic.Uint64`——第七章说它"跨轮次、跨重启会重号"，现在进程内唯一了，重启会归零但 CallID 本来就不是唯一键，够用。


4. 观测点前移：从消费路径回到事件源头

把第七章的记账代码和本章的并排看：

```go
// 第七章：挂在事件消费侧
if out.IsStreaming {
    if err := em.ConsumeStream(out.MessageStream); err != nil { ... }
    recordUsage(em.PopUsage())          // 只有 ConsumeStream 正常返回才执行
} else if out.Message != nil {
    ...
    recordUsage(out.Message.ResponseMeta.Usage)   // 非流式还要单写一路
}

// 本章：挂在事件源头（WrapModel 内部），消费侧什么都不用做
```

三个实际收益，不是审美：

1. **重试的每次 attempt 都有账**。retry 包装在 WrapModel 之外，每次重试都会重新经过 usage 中间件——一次"空输出重试成功"的调用，账本上是两行明细（一行空转、一行有效），和真实发生的 API 调用一一对应。第七章的消费侧记账对重试一无所知；
2. **不依赖前端事件流被消费**。只要模型被调用，账就记了——将来任何绕过 emitter 的调用路径（后台任务、批处理、子代理的内部调用）自动入账，不需要谁记得补一行 `recordUsage`；
3. **emitter 回归纯协议生产者**。`streamUsage` 字段、`mergeUsage`、`PopUsage` 三个成员整体删除，第七章 6.1 说的"协议的生产者住进协议包"再进一步：只生产协议，不兼职记账。一个结构体一个职责，改动面实打实小了 31 行。

代价要说清楚：中断场景的账目变化还没实测。ctx 取消时流被消费方提前 Close，`WithOnEOF` 是否还触发、第七章"停止的半截没账"是否被这次搬家顺手修好——要跑一次停止操作对着表看（遗留清单第 7 条）。搬家修的是覆盖面，不是承诺把每一笔都收齐。


5. rctx：ctx 值总线与中间件无状态化

5.1 一个包收编四类值

`trace/session.go` 整体退役，值通道泛化成独立包：

```go
// internal/agentkit/rctx/ctx.go（节选）
func WithSessionId(ctx context.Context, sid int64) context.Context
func GetSessionID(ctx context.Context) (int64, bool)
func WithMessageID(ctx context.Context, mid int64) context.Context
func WithModelName(ctx context.Context, name string) context.Context
func WithBizCode(ctx context.Context, bizCode string) context.Context
```

搬家的理由不是洁癖：原来这套 Set/Get 住在 trace 包里，而 trace 只是第一个消费者——本章 usage 中间件同样要读 sessionID 和 modelName，让它 import trace 就闹了"观测中间件依赖日志组件"的笑话。值通道从第一个消费者家里搬出来自立门户，谁都能 import，谁也不拥有它。trace 的五个钩子改一行 `rctx.GetSessionID(ctx)`，行为不变。

Runner 里的注入时序原样保留，第七章 4.3 那条"对着源码才敢写"的发现继续有效：

```go
// internal/agentkit/chatagent.go（节选）
runner := adk.NewRunner(ctx, adk.RunnerConfig{...})   // 这个 ctx 会被 NewRunner 忽略
// 注入sessionId与模型名，usage 中间件落库时从 ctx 读取归属信息
ctx = rctx.WithSessionId(ctx, int64(sessionID))
ctx = rctx.WithModelName(ctx, e.build.ModalName)
agevs := runner.Run(ctx, message, ...)
```

6. Agent 生命周期：构建一次，缓存复用

6.1 旧账：每条消息都 deep.New

第七章之前的构建路径是两段式：`getSession` 返回一个 workspace（缓存了构建参数和模型实例），然后 `buildAgent` **每次 Runner 调用都重新 `deep.New` 一遍**——挂工具、拼提示词、建图，一条消息一次。deep agent 的构建不是免费的：内部要注册 write_todos、filesystem 工具中间件、建 task 子代理。更要命的是提示词在构建时拼死，运行时改配置不生效。

本章把"构建产物"整个缓存下来：

```go
// internal/agentkit/chatagent.go（节选）
type entry struct {
    build *provider.BuildParams
    fp    string // 构建参数指纹
    agent adk.ResumableAgent
    // runMu 串行化同一会话的运行：entry 里的 agent 与 middleware 实例被同会话
    // 所有请求共享，并发 Run 会踩彼此的状态，也和历史消息/checkpoint 交错
    runMu sync.Mutex
    // lastAccess 供空闲淘汰判断，getEntry 命中或新建时刷新
    lastAccess time.Time
}
```

```go
// getEntry 核心：指纹一致直接复用缓存
fp, err := buildFingerprint(fpStr)
...
c.mu.Lock()
defer c.mu.Unlock()
if e, ok := c.entries[sessionID]; ok && e.fp == fp {
    e.lastAccess = now
    return e, nil
}
// 不存在或指纹变化，重建
```

指纹是构建参数（key/地址/模型名）的 sha256——模型接入变了才重建，否则复用。`deep.New` 从热路径上消失，工具注入失败/无工具两行日志也只在重建时打。

6.2 runMu：同会话串行化

缓存把并发问题带出来了：同一个 entry 会被同会话的多个请求 goroutine 拿到，agent 与 middleware 实例共享，并发 Run 会踩状态、历史消息和 checkpoint 会交错。`runMu.Lock()` 放在 Runner 入口，同会话请求排队，跨会话不互斥——粒度刚好。

6.3 有界淘汰：清理成本摊在新建路径

```go
const (
    maxEntries = 32
    idleTTL    = 30 * time.Minute
)

// evictIdleLocked 清理长期不用的 entry，调用方需持有 c.mu。
// runMu 占用中的 entry 正在运行，跳过：删 map 不影响进行中的 run，但会让
// 同会话下一个请求重建 entry、与旧 run 失去串行化，不如不删。
```

三个决定值得记：**无后台 goroutine**——清理挂在低频的"新建 entry"路径上顺带做，桌面应用不需要一个只为扫地活着的协程；**TryLock 探测**——`runMu` 被占说明在跑，跳过不删，删了会让同会话下一个请求和旧 run 失去串行化；**会话删除不主动淘汰**——services 的 Delete 靠空闲淘汰兜底（自增主键不会被复用，陈旧 entry 只是占 30 分钟内存）。`Evict(sessionID)` 作为主动回收口子导出了，但目前没有调用方——备而未用，账记上。

淘汰逻辑自己有一处真 bug，放在遗留清单第 1 条：`evictIdleLocked` 的注释要求"调用方需持有 c.mu"，`getEntry` 却在 `c.mu.Lock()` **之前**调用了它——并发 map 读写，这是要 fatal 的。修法一行：挪进锁内。诚实记录，下一章第一件事修它。

6.4 ModelRetryConfig：什么错值得再试一次

```go
ModelRetryConfig: &adk.ModelRetryConfig{
    MaxRetries: 5,
    ShouldRetry: func(ctx context.Context, retryCtx *adk.TypedRetryContext[*schema.Message]) *adk.TypedRetryDecision[*schema.Message] { ... },
},
```

决策表（ShouldRetry 的四个分支）：

| 场景 | 决策 |
| --- | --- |
| ctx 取消 | 一律不重试（用户点了停止就是停止） |
| 429 / 5xx / timeout / connection refused | 重试，指数退避 `2^attempt × 200ms` |
| 400 / 401 / 403 / 内容安全拦截 | 终止，重试无意义 |
| 无错误但空输出（无文本且无 tool_calls） | 重试，往输入追加一条"请返回有效内容，不要返回空"，且不落历史 |

最后一个分支是"采样后验证"的本地化——Claude Code 的 Stop Hook 说"做完了才能停"，这里是"结果有效才算数"。两个边界拿捏值得抄：**ToolCall 存在时 Content 为空是正常的**（模型决定调工具，本来就没有文本），只有两者皆空才判无效，否则会打死所有工具调用轮次；`PersistModifiedInputMessages: false`——那条催促语是给模型的临时提词，不该进对话历史污染上下文。重试和 usage 的协同在 3.4 说过：retry 包在 WrapModel 之外，每次 attempt 单独记账。

8. 工具配置换源：从数据库表到 .conf/tools.json

8.1 seed 机制为什么整体退役

删掉的东西列一下，合计约 170 行：`internal/data/seed.go`（104 行）、`tool.json`（种子文件）、`migrations/create_tools.sql`、main.go 里的 `go run . seed` 子命令、`po.Tool`（GORM 模型）。

理由不是"数据库不好"，是**这个数据的性质配不上这套机制**。第六章上数据库时预设的工具形态是"平台里有几十上百个工具、参数模板要版本化合并、多用户共享一套配置"——桌面单机应用的现实是：工具三五个，配置就是一份 apiKey + 一个 url，只有一台机器一个用户在读它。为三五份配置养一张表、一个 seed 命令、一套"按 label 合并不覆盖用户已填值"的合并算法，机制和数据规模差着两个数量级。

Claude Code 的对照做法是 settings.json——Hook 配置、权限规则全在文件里，多来源合并治理的是"来源"而不是"存储引擎"。taie 学的是这个方向：配置的数据，用配置文件的形态。

8.2 ConfigFile[T]：原子写的泛型配置文件

```go
// internal/pkg/utils/file.go
type ConfigFile[T any] struct {
    mu   sync.Mutex
    path string
}

func (c *ConfigFile[T]) writeFile(v T) error {
    bytes, err := json.MarshalIndent(v, "", "  ")
    ...
    // 创建临时文件，防止奔溃损坏数据
    tmpPath := c.path + ".tmp"
    if err := os.WriteFile(tmpPath, bytes, 0644); err != nil { ... }

```

泛型读改装进 `internal/pkg/utils`：Load/Save 两个方法，进程内互斥锁串行化，写路径走"临时文件 + rename"——写一半崩溃不会留下半个 JSON。70 来行，`tools.json` 是第一个用户，将来的 agent 配置、项目配置都走它。

8.3 主键换成 toolName，顺手销一笔旧账

```go

type ToolConfig struct {
```

9. 读路径：账本的另一半与会话回放

第七章把账记上了，本章把账读出来。`internal/data/token.go` 三个聚合查询：按天（`date(created_at, 'localtime')` 分组，SQLite 的 localtime 修饰符把带时区的时间文本转本地日期）、按会话、按模型，统一支持"最近 N 天"过滤。按会话那条值得看一眼：
