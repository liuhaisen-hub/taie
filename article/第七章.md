1. 本章目标

结束时你将得到：

- 全局日志落盘：`log/slog` + lumberjack 滚动日志（10MB × 5 份 × 10 天，自动压缩），桌面应用的路径坑（`go run` 的临时二进制目录）有兜底；全局单例让 `logger.Info(...)` 和 `slog.Info(...)` 汇入同一个文件；
- Agent 全链路 trace：实现 eino 的 `callbacks.Handler` 五个钩子，组件级的 START / END / ERROR 结构化日志——模型调用、工具执行每一步都留痕，sessionID 经 ctx 贯穿到每一行；
- token 用量落库：第六章铺的 `session_token_usage` 表迎来第一笔写入——流式 usage 从流末尾空帧捕获、按字段取 max 合并防网关重复上报，非流式从 `ResponseMeta` 直取；
- emitter 搬家：从 `chatagent.go` 收编进 `internal/pkg/events`——协议的生产者搬进协议包；顺手一次协议收缩：**工具入参不再回传前端**；
- 装配升级：`*slog.Logger` 成为 wire 的注入源，main 里 `logger.Get()` 一处初始化，任何构造函数按需声明参数即可拿到。


2. 全景：三条观测线

上一章结尾预告的是 MCP，本章实际到岗的是可观测性——不算跳票，是顺序问题：`docs/` 里已经躺着工具审批的施工图，Agent 马上要开始"真干活"（接 MCP、跑工具、等人审），干活之前得先装行车记录仪。另一个更直接的动因：第六章铺的 `session_token_usage` 表不能永远躺着。

可观测性回答三个问题：

1. **出了事有没有现场？** → logger：应用日志滚动落盘，出问题翻文件；
2. **Agent 内部每一步在干嘛？** → trace：eino 执行图里每个组件（ChatModel、ToolsNode）的开始/结束/出错都有结构化日志；
3. **这一轮烧了多少 token？** → usage：每次模型调用一行明细进库，给将来的用量统计 Tab 备料。

三条线从 Runner 分出：

```
                 ┌─ logger（slog + lumberjack）──────────► logs/app.log（滚动压缩）
                 │
ChatAgent.Runner ┼─ trace.Tracer（eino callbacks 五钩子）──► 组件级结构化日志行
                 │
                 └─ recordUsage（流式 / 非流式两条路）─────► session_token_usage 表
                                                              └─► 用量统计 Tab（下一章前端）
```

分工原则一句话：**日志给人翻，trace 给排障，usage 给算账**。三者都遵守同一条铁律——观测失败不影响业务：trace 的钩子只写日志不返回错误，usage 落库用 `_ =` 吞错，日志写盘由 lumberjack 的有界策略兜底。


3. logger 包：标准库解决战斗

3.1 选型：slog + lumberjack，只加一个依赖

```go
// internal/pkg/logger/logger.go
func NewLogger() *slog.Logger {
    lumberWriter := &lumberjack.Logger{
        Filename:   getLogFilePath(),
        MaxSize:    10,       // MB，单文件上限
        MaxBackups: 5,        // 最多留 5 个旧文件
        MaxAge:     10,       // 天
        Compress:   true,     // 旧文件压缩
        LocalTime:  true,
    }
    handler := slog.NewTextHandler(lumberWriter, &slog.HandlerOptions{
        Level: slog.LevelInfo,
    })
    return slog.New(handler)
}
```

为什么不上 zap / logrus：桌面应用的日志量级用不到 zap 的零分配黑科技；`log/slog` 已经进了标准库，结构化字段、级别、handler 抽象一样不缺；最关键的是 handler 是可组合的装饰器——本章的 `AsyncHandler` 就是往这个口子上插的（见 3.4）。go.mod 里唯一的新依赖是 `gopkg.in/natefinch/lumberjack.v2`，专职滚动删旧，各司其职。

3.2 日志写在哪：一个两分支的坑

```go
// 日志写到可执行文件所在目录的 logs/ 下
func getLogFilePath() string {
    if exePath, err := os.Executable(); err == nil {
        // go run / go test 时可执行文件在临时构建目录里，此时退回到工作目录下的 logs/
        if !strings.HasPrefix(exePath, os.TempDir()) {
            return filepath.Join(filepath.Dir(exePath), "logs", "app.log")
        }
    }
    return filepath.Join("logs", "app.log")
}
```

坑在 `os.Executable()`：`go run` 时二进制被构建到 `os.TempDir()` 下的临时目录，跟着它走日志就写进系统临时文件夹了——用 TempDir 前缀判断识别这种情况，回退到工作目录。打包后的 mac 应用二进制在 `.app/Contents/MacOS/` 里，日志也跟着进包内——升级替换包时日志会一起没了，要不要挪到 `~/Library/Application Support`，遗留清单记一笔。

3.3 全局单例：两条使用路径并存

```go
// 全局单例：任意包 import 后通过 Get() / 便捷函数使用，首次调用时初始化。
var (
    once   sync.Once
    global *slog.Logger
)

// Get 返回全局 logger，并在首次调用时将其设为 slog 的默认 logger
// （之后 slog.Info 等原生函数也会写入同一个日志文件）。
func Get() *slog.Logger {
    once.Do(func() {
        global = NewLogger()
        slog.SetDefault(global)
    })
    return global
}

// 便捷函数：业务代码直接 logger.Info("msg", "key", val) 即可，无需持有实例。
func Info(msg string, args ...any) { Get().Info(msg, args...) }
```

`slog.SetDefault` 是点睛之笔：之后**任意包里的原生 `slog.Info(...)` 也会写进同一个文件**（Go 1.21 起连标准库 `log` 的默认输出都跟着汇入）。于是包里有两条合法的获取路径：

- **DI 路径**：wire 构造函数声明 `*slog.Logger` 参数，测试时可注入假实现；
- **全局路径**：不想改签名的老代码直接 `logger.Info(...)`。

两条路通向同一个文件，没有第二份初始化逻辑——`sync.Once` 保证的。

3.4 AsyncHandler：备而未用

```go
// internal/pkg/logger/asyn.go
func (a *AsyncHandler) Handle(ctx context.Context, r slog.Record) error {
    select {
    case a.ch <- r:
    default:
        // 队列满，丢弃日志，防止阻塞业务
    }
    return nil
}
```

一个标准的异步 handler 骨架：有界 channel 做队列，入队是非阻塞的（满了就丢），单个后台协程消费写入内层 handler；`WithAttrs / WithGroup` 共享同一个通道。**"丢日志保业务"是刻意的权衡**——桌面应用的 UI 线程不能被磁盘 I/O 卡住，观测数据的优先级天然低于业务。

但要诚实记录：**`NewLogger` 目前接的还是同步的 `TextHandler`，`AsyncHandler` 写完没接线**。队列机制躺在那里等一个"日志量大到影响 UI"的时刻，接上它只需改 `NewLogger` 一行——顺带得补一个现在没有的东西：优雅关闭（没有 flush，退出时队列残留会丢）。


4. trace 包：给 eino 装行车记录仪

4.1 eino callbacks 机制，30 秒版

eino 的执行图（graph / adk agent）内建了回调机制：任何组件被调用时，框架会沿 ctx 找到注册的 `callbacks.Handler`，按五个时机通知它：

| 钩子 | 时机 |
| --- | --- |
| `OnStart` / `OnEnd` | 非流式：组件开始前 / 成功返回后 |
| `OnError` | 组件返回非 nil error 时 |
| `OnStartWithStreamInput` / `OnEndWithStreamOutput` | 流式进 / 流式出（handler 收到的是流的副本） |

每个钩子都带 `*callbacks.RunInfo`（组件名 `Name` + 类型 `Type`，比如 `ChatModel`、`ToolsNode`）和 ctx——**ctx 是贯穿执行图的**，这正是把 sessionID 带进每条日志的通道。注册方式是 Run 选项：`adk.WithCallbacks(handler)` 返回 `AgentRunOption`，每次 `runner.Run(...)` 传一次。

4.2 Tracer：五个钩子的处理

```go
// internal/agentkit/trace/trace.go（节选）
type Tracer struct {
    logger *slog.Logger
    prefix string
}

// 返回具体类型 *Tracer 而非接口，wire 才能把它注入到 NewChatAgent
func NewLogCollectHandler(logger *slog.Logger) *Tracer {
    callbacks.AppendGlobalHandlers()
    return &Tracer{
        logger: logger,
        prefix: "[AGENT_LOG]",
    }
}

func (t *Tracer) OnStart(ctx context.Context, info *callbacks.RunInfo, input callbacks.CallbackInput) context.Context {
    sessionID, _ := GetSessionID(ctx)
    msg := fmt.Sprintf("%s START sessionId: %d", t.prefix, sessionID)
    t.logger.Info(msg,
        "component", info.Name,
        "type", info.Type,
        "input", input,
    )
    return ctx
}
```

五个钩子是同一个模式：从 ctx 取 sessionID，打一行结构化日志，原样返回 ctx。两个值得记的细节都在流式钩子的注释里：

```go
func (t *Tracer) OnEndWithStreamOutput(ctx context.Context, info *callbacks.RunInfo,
    output *schema.StreamReader[callbacks.CallbackOutput]) context.Context {
    ...
    // output 是流，不要直接打印，会吃掉流数据
    return ctx
}
```

**handler 收到的流是副本，但"读了副本不影响业务"只对框架保证的拷贝语义成立；习惯上流式钩子一律不消费流**——要看内容得开 goroutine 单独读副本。eino 源码还有一条边界值得抄下来：`OnError` 只上报组件直接返回的错误，**流中途的错误不在 OnError 里出现，它们以流读取错误的形式浮现**——所以"流读到一半炸了"在日志里看到的是对应组件的 OnEnd 缺失，而不是一条 ERROR。排障时要知道这个盲区。

顺带说明 `TimingChecker`：eino 还有个可选接口，handler 声明"我只关心哪几个时机"，框架就能跳过其余时机的流拷贝开销。Tracer 五个时机全要，所以没实现它——这个接口是留给将来的精简型 handler 的。

4.3 sessionID 进 ctx 的时序

```go
// internal/agentkit/trace/session.go
type sessionIDKey struct{}   // 空结构体做 key：零分配且天然防碰撞
type messageIDKey struct{}   // 预留，还没人写

func SetSessionID(ctx context.Context, sid int64) context.Context {
    return context.WithValue(ctx, sessionIDKey{}, sid)
}
func GetSessionID(ctx context.Context) (int64, bool) {
    val, ok := ctx.Value(sessionIDKey{}).(int64)
    return val, ok
}
```

Runner 里的接入顺序值得单独看一眼：

```go
// internal/agentkit/chatagent.go（节选）
runner := adk.NewRunner(ctx, adk.RunnerConfig{...})
// 注入sessionId
ctx = trace.SetSessionID(ctx, int64(sessionID))
agevs := runner.Run(ctx, message,
    adk.WithSessionValues(map[string]any{...}),
    // 接入日志
    adk.WithCallbacks(c.tracer),
)
```

`SetSessionID` 放在 `NewRunner` **之后**、`Run` **之前**——看似随手，实际恰好正确：对照 eino v0.9.20 源码，`NewRunner(_ context.Context, conf)` 的 ctx 参数**是被忽略的**（`_`），只有传给 `Run` 的 ctx 会流进执行链路、被每个组件的回调看到。这是一处"对着源码才敢写的顺序"，注释里没写，文章里记一笔。

4.4 一个诚实的小注脚：AppendGlobalHandlers() 是空操作

构造函数里那句 `callbacks.AppendGlobalHandlers()` 零参调用——对照源码，它的实现是 `GlobalHandlers = append(GlobalHandlers, handlers...)`，**零参等于什么都没加**。它想表达的意图（"确保全局回调机制就绪"）不需要这行也能成立：`adk.WithCallbacks` 每次 Run 传 handler 已经够用。这行要么删掉，要么等真需要进程级全局挂载时把 Tracer 传进去——现在它只是个心理安慰。

4.5 返回具体类型，不返回接口

`NewLogCollectHandler` 返回 `*Tracer` 而不是 `callbacks.Handler` 接口——注释里写了原因："wire 才能把它注入到 NewChatAgent"。这和第二章"接口归消费方"不矛盾，反而是那个模式的边界说明：**接口模式适用于"data 实现消费方声明的接口"**（repo 类依赖，多个实现可替换）；**运行时组件直接注入时，构造函数返回具体类型最简单**——wire 按参数类型连线，返回接口反而让它不知道该拿谁满足 `*Tracer` 参数。想两者兼得可以用 `wire.Bind`，本章没必要。


5. token 用量：session_token_usage 的第一笔写入

5.1 recordUsage：一个闭包管记账

`AgentRepo` 长出第五个方法（接口归消费方，data 实现），data 层一行 `Create`：

```go
// internal/data/agent.go
// AppendTokenUsage 落库一行 token 消耗明细（每次模型调用一条）
func (a *agentRepo) AppendTokenUsage(ctx context.Context, u *po.SessionTokenUsage) error {
    return a.data.db.WithContext(ctx).Create(u).Error
}
```

Runner 里建一个闭包管记账：

```go
// internal/agentkit/chatagent.go（节选）
// 每次模型调用记一行 token 明细；usage 是否返回由模型/网关决定，拿不到或全 0 时跳过
callSeq := 0
recordUsage := func(u *schema.TokenUsage) {
    if u == nil || (u.PromptTokens == 0 && u.CompletionTokens == 0 && u.TotalTokens == 0) {
        return
    }
    callSeq++
    _ = c.repo.AppendTokenUsage(ctx, &po.SessionTokenUsage{
        SessionID:        uint64(sessionID),
        CallID:           fmt.Sprintf("chatmodel-%d-%d", sessionID, callSeq),
        ModelName:        e.Build.ModalName,
        PromptTokens:     u.PromptTokens,
        CompletionTokens: u.CompletionTokens,
        TotalTokens:      u.TotalTokens,
    })
}
```

四个设计点：

1. **跳过 nil / 全 0**：usage 能不能拿到取决于模型网关（OpenAI 兼容协议要 `stream_options.include_usage`，eino 的 OpenAI 绑定流式固定带上了它；但别的兼容网关未必回）。拿不到就静默跳过——账本宁缺毋错；
2. **CallID 是轮内序号**：`chatmodel-{session}-{callSeq}`，`callSeq` 是 Runner 调用内的局部变量——一次问答里模型可能被调多次（工具调用前后各一次），每行明细按序编号。它标识"这轮的第几次调用"，**不是全局唯一键**（跨轮次、跨重启会重号），表设计留的 `CallID VARCHAR(128)` 注释写的"Eino callback调用ID"是它的远景，现在先当轮内序号用；
3. **ModelName 取自会话快照**（`e.Build.ModalName`）——第五章"会话冻结模型接入"的语义在账单上同样成立：老会话换了全局模型，用量明细里记的还是当时快照的那个名字；
4. **`_ =` 吞错**：观测失败不影响业务——和 trace 只写日志不返回错误、`em.interrupted()` 静默收口是同一条铁律。

调用点两条路：

```go
if out.IsStreaming {
    if err := em.ConsumeStream(out.MessageStream); err != nil { ... }
    recordUsage(em.PopUsage())          // ⬅ 流式：一条流 = 一次调用，EOF 后取
} else if out.Message != nil {
    if err := em.AssistantMessage(out.Message); err != nil { ... }
    if out.Message.ResponseMeta != nil {
        recordUsage(out.Message.ResponseMeta.Usage)   // ⬅ 非流式：直接取
    }
}
```

5.2 流式 usage 藏在哪，为什么要按 max 合并

流式的 usage 不在正文分片里——OpenAI 协议把它挂在**流末尾那个空内容帧**的 `ResponseMeta.Usage` 上。正文分支和工具调用分支都不消费它，所以捕获要单独做，位置就在 emitter 消费流的地方：

```go
// internal/pkg/events/emiter.go（节选）
// usage 通常在流末尾空内容帧上，正文/工具调用分支都不消费它，这里单独捕获
if chunk.ResponseMeta != nil && chunk.ResponseMeta.Usage != nil {
    e.mergeUsage(chunk.ResponseMeta.Usage)
}

// mergeUsage 按 max 合并 usage，与 schema.ConcatMessage 同规则，
// 防个别网关在多个 chunk 上重复携带 usage 导致累加虚高。
func (e *emitter) mergeUsage(u *schema.TokenUsage) {
    if e.streamUsage == nil {
        e.streamUsage = &schema.TokenUsage{}
    }
    if u.PromptTokens > e.streamUsage.PromptTokens {
        e.streamUsage.PromptTokens = u.PromptTokens
    }
    ... // CompletionTokens / TotalTokens 同理
}

// PopUsage 取出并清空当前流式消息的 token 用量，一次模型调用读一次。
func (e *emitter) PopUsage() *schema.TokenUsage {
    u := e.streamUsage
    e.streamUsage = nil
    return u
}
```

合并规则是个容易想错的点：**为什么按字段取 max，而不是累加？** 因为 token 用量是"本次调用累计"语义——正规实现只在最后一帧带一次全量；但个别网关会在多个 chunk 上重复携带同一份 usage，累加就虚高数倍。eino 自己的 `schema.ConcatMessage` 拼消息时也用同样的 max 规则，这里保持一致。`PopUsage` 取出即清空，一条流对应一次模型调用，不会把上一轮的量记到下一轮头上。

5.3 一个语义缺口：被中断的调用没有账

`recordUsage(em.PopUsage())` 只在 `ConsumeStream` **正常返回**后才执行；用户点停止时 ctx 已取消，`ConsumeStream` 提前返回错误，走中断落库分支——那条路没有 recordUsage，而且即便调了，ctx 取消后 `gorm.WithContext(ctx)` 的写入也会直接失败。结果：**停止的那半截回答，token 烧了但没记账**。修法方向也明确——中断路径用 `context.WithoutCancel(ctx)`（Go 1.21+）补最后一笔。遗留清单见。


6. emitter 搬家：协议的生产者住进协议包

6.1 为什么搬

上一章的 emitter 住在 `chatagent.go` 里，占了约 190 行——协议定义在 `internal/pkg/events`，协议的生产却在 `internal/agentkit`，改一个事件形状要同时动两个包。本章把它整体搬进 `internal/pkg/events/emiter.go`：**协议的词表（ContentItem / Event）和协议的生产者（emitter）从此住在一起**。`chatagent.go` 从 421 行瘦到 251 行，Runner 的循环里只剩业务语义（工具回执、流式消费、中断落库），事件的拼装细节一个都看不见了。

跨包引用要求方法导出，顺带完成了一次命名升级：

| agentkit 时代（私有） | events 时代（导出） |
| --- | --- |
| `newEmitter` | `NewEmitter` |
| `consumeStream` | `ConsumeStream` |
| `toolResult` | `ToolResult` |
| `done` / `interrupted` | `Done` / `Interrupted` |
| （新增） | `PopUsage` |

`delta / streamEOF / streamAcc / emitToolCall / mergeUsage` 保持私有——它们是内部齿轮，外面没人需要认识。

6.2 顺手一次协议收缩：工具入参不回传前端

搬家不是平移，带了一处行为变更：

```go
// toolCallAcc 聚合一条工具调用的流式分片：eino 的 chunk.ToolCalls 按 Index 分片，
// Name/ID 可能只在首个分片出现。入参分片直接丢弃（不回传前端）。
type toolCallAcc struct {
    id   string
    name string
}
```

上一章的聚合器还攒 `args strings.Builder`，EOF 时把完整入参 JSON 塞进 `function_call` item 下发；本章把 `args` 字段删了，`ToolCall` 事件从四参缩成三参——**前端收到的工具调用卡片不再带 arguments**（`event.go` 的注释原话："工具入参不回传，前端只展示'正在调用xx工具'"）。前端 `types.ts` 里的 `arguments?: string` 字段保留为预留位，Semi 原生渲染对它的缺省也无感。

理由值得展开：工具入参是**模型的内部决策**，不是给用户看的内容——折叠卡上展示一坨 JSON 参数没有信息价值，还可能把敏感内容（比如搜索词以外的上下文片段）直接上屏。展示做减法的同时，运维视角是全量的：ToolsNode 的 START 日志 input 里能看到模型发起的完整工具调用（含入参 JSON，见第 8 节）。要对照第六章的表述说一声抱歉——那里还写着"Arguments 逐片追加"，两章之内自我推翻，这次记下变更原因，下次别再改回来。

6.3 一笔要认的账："零依赖协议包"退役

第五章给 `internal/pkg/events` 立过规矩，原话："它不 import adk、eino、gorm、wails 里的任何东西，只定义纯数据结构"——依赖解耦靠 import 图机械保证。emiter.go 打破了字面规矩：它需要 `*schema.StreamReader`、`schema.Message`、`schema.TokenUsage`，**import 了 `eino/schema`**。

辩护与认账各一半：

- **辩护**：`schema` 是 eino 的词表包（消息、流、用量的类型定义），不拖 `adk / compose` 的执行栈。真正"重"的部分——adk、compose——仍然只有 agentkit import，这条底线没破。services 拿到的传递依赖增量是"一个词表包"，可控；
- **认账**："零依赖"这个词从此不许再说了。准确的新说法是"**词表级轻依赖**"。如果哪天要把字面规矩也捡回来，路径是把 emitter 的流参数抽象成接口（比如只暴露 `Recv/Close` 的最小流接口），让 events 不认识 eino——目前不值得。

架构决策的表述要跟着代码走：规矩破了就更新表述，别让文档比代码乐观。


7. 装配：*slog.Logger 作为注入源

```go
// main.go
// Get() 初始化全局单例并 slog.SetDefault：之后任意包可 logger.Info(...) / slog.Info(...)。
// 同时作为依赖传入 Wire——wire.go 里声明 *slog.Logger 参数的构造函数按需拿到它。
wailsApp, cleanup, err := InitializeApp(logger.Get())
```

```go
// wire.go
// *slog.Logger 是注入源：main 把全局 logger 传进来后，
// wire.Build 里任何构造函数声明 *slog.Logger 参数即可按需拿到它，
// 不需要的构造函数不用改签名。
func InitializeApp(log *slog.Logger) (*application.App, func(), error)
```

```go
// wire_gen.go（生成产物，节选）
tracer := trace.NewLogCollectHandler(log)
chatAgent := agentkit.NewChatAgent(agentRepo, checkPointStore, tracer)
```

`agentkit.ProviderSet` 加了一行 `trace.NewLogCollectHandler`，wire 链就多了一节：`logger.Get()` → `NewLogCollectHandler` → `NewChatAgent` 的第三个参数。这个"注入源"模式的妙处在 wire.go 注释里写得直白：**`*slog.Logger` 声明在构造函数参数里是按需的**——不需要日志的构造函数（比如 `NewToolsRepo`）签名一个字不用动，需要的（`NewLogCollectHandler`）自然被供给。全局单例负责"到处能用"，注入负责"该拿的人拿到的和全局是同一个"。


8. 一次真实问答的留痕

发起一次带工具调用的问答（"我想知道当前美国经济受什么影响"），logs/app.log 里大致是这几行：

```
time=2026-09-29T14:35:02+08:00 level=INFO msg="[AGENT_LOG] START sessionId: 1" component=ChatModel type=ChatModel input=…
time=2026-09-29T14:35:05+08:00 level=INFO msg="[AGENT_LOG] STREAM_OUTPUT END sessionId 1" component=ChatModel type=ChatModel
time=2026-09-29T14:35:05+08:00 level=INFO msg="[AGENT_LOG] START sessionId: 1" component=ToolsNode type=ToolsNode input=…   ← 工具调用与完整入参在这
time=2026-09-29T14:35:06+08:00 level=INFO msg="[AGENT_LOG] END sessionId: 1" component=ToolsNode type=ToolsNode output=…
time=2026-09-29T14:35:06+08:00 level=INFO msg="[AGENT_LOG] START sessionId: 1" component=ChatModel type=ChatModel input=…
time=2026-09-29T14:35:09+08:00 level=INFO msg="[AGENT_LOG] STREAM_OUTPUT END sessionId 1" component=ChatModel type=ChatModel
```

对应的 DB 写入：`chat_message` 两行（user + assistant），`session_token_usage` **两行**——第一次 ChatModel 调用（决定调工具）一行 `chatmodel-1-1`，工具结果喂回去后的第二次调用一行 `chatmodel-1-2`。账本和日志能对上：几次 START ChatModel 就几行用量。

排障路径从这三样数据各自长出来：

| 症状 | 去哪查 |
| --- | --- |
| 前端卡片没归位 / 回答中断 | 日志里找 `[AGENT_LOG] ERROR`；没有 ERROR 但 OnEnd 缺失 → 流中途出错（见 4.2 的盲区） |
| 模型到底传了什么参数给工具 | ToolsNode START 的 input（前端已不展示入参，日志是唯一现场） |
| 这轮烧了多少 token | `session_token_usage` 按 session_id 查，CallID 序号对应第几次模型调用 |
| 应用重启后问题复现不了 | 日志文件还在（10 天滚动），DB 数据还在——这就是"留痕"的意义 |


9. 铺路清单与遗留清单

**本章铺的路**

| 铺设物 | 等谁 |
| --- | --- |
| `AsyncHandler`（有界队列 + 丢弃语义 + 后台消费） | 日志量上来之后的零阻塞改造，接线只差 `NewLogger` 一行 |
| `trace.session.go` 的 `messageIDKey`（Set/Get 已备） | 消息级追踪：等消息 ID 有了稳定来源就接线 |
| `session_token_usage` 的写入通路 | 用量统计 Tab（读的那一半，下一章前端） |
| `types.ts` 的 `arguments?: string` 预留位 | 哪天要把入参以"展开查看"形式还给前端 |
| `docs/agent-event-and-approval.md` 施工图 | 工具审批（人审中断/恢复），连 checkpoint 的雷都标好了 |

**新账**

1. **被中断的调用没有用量账**：ctx 取消后 `recordUsage` 不被调用、也调不通（见 5.3）——停止的那半截最贵（prompt 里有全部历史），却没进账本。修法：中断路径用 `context.WithoutCancel(ctx)` 补记；
2. **`AsyncHandler` 写了没接线**：`NewLogger` 还是同步 `TextHandler`；接上时要连优雅关闭一起补（现在没有 flush，退出丢尾部日志）；
3. **`AppendGlobalHandlers()` 零参空操作**（见 4.4）：要么删，要么真传 handler 做全局挂载；
4. **`session_token_usage.MessageID` 永远是 NULL**：emitter 的 assistantID 是临时 ID（`assistant-{session}-{nanotime}`），和 `chat_message` 落库后的自增主键没打通——要关联得落库后回填，或预生成消息 ID；
5. **打包后日志随安装包走**：mac 应用日志在 `.app/Contents/MacOS/logs/` 里，升级即失。该挪 `~/Library/Application Support` 了，趁日志还没被用户当宝贝；
6. **trace 的内容盲区是双向的**：流式钩子刻意不记内容（正文排查靠落库），工具内部的 HTTP 细节也不在观测范围（web_search 的耗时、重试只有那一行 ToolsNode END 的 wall time）——组件级 trace 够用，但别指望它回答"搜索 API 为什么慢"；
7. **BuildTools 静默 continue 还是没日志**（第六章第 10 条沿用）：讽刺的是本章把日志系统建好了，隔壁注册表构建失败依旧无声无息——一行 `logger.Warn` 的事，下一章谁动 toolkit 谁顺手还上；
8. **拼写家族再添一员**：`emiter.go`（emitter 少个 t）。加上 `Workespace` / `prmopt.go` / `creat_message.sql`，凑一桌麻将了。上一章说"改一次成本最小的时候是今天"，今天显然不是，继续记账。

**沿用**（一字未动，索引见第六章第 11 节）：checkpoint 列名不一致、extra.model 不消费、`buildMessage` 硬编码 40、出错路径不落库、`SessionRepo.Update` 列名写法、启用守卫对 `[]` 失效、`modeName` 笔误、CommonJson 全 string、停止时 UI 与 DB 的文本差。值得点名的是"**出错路径不落库**"和本章的"中断没账"同根：**中断与出错的收口路径是整个系统的观测盲区**——消息不落库、用量不记账、trace 只有零星 ERROR，下次修收口逻辑时把三样一起补。
